# Проверка вхождения в большом наборе

## Генерация

Опиши рабочую ситуацию: младший разработчик пишет скрипт на Python для задачи: {domain}. Есть два набора записей: первый скрипт перебирает, а во втором ищет каждую запись первого. Приведи в блоке кода фрагмент скрипта из 4–8 строк: идентификаторы второго набора собраны в обычный список Python, а цикл по первому набору проверяет каждую запись оператором `in` по этому списку. Расскажи, сколько записей в наборах, сколько скрипт работает сейчас и что коллега хочет поменять в следующей версии

## Вопросы

1. Оцените, сколько операций выполняет скрипт сейчас, и объясните, почему он работает так долго.
2. Какую структуру данных стоит использовать для второго набора? Как она устроена внутри и какова сложность проверки вхождения в среднем и в худшем случае?
3. Какова сложность всего скрипта после исправления, с учётом подготовки этой структуры?
4. Что произойдёт, если сделать ключом список из двух значений, как хочет коллега, и как это исправить?
5. Если по найденному идентификатору нужно ещё получить остальные поля записи второго набора, что вы используете?

Ответ — развёрнутый текст на 10–20 предложений

## Факты

- list-lookup: идентификаторы второго набора хранятся в обычном списке Python, и скрипт проверяет вхождение оператором `in` по этому списку
- loop: проверка вхождения выполняется в цикле для каждой записи первого набора
- sizes: в первом наборе около 200 тысяч записей, во втором — около 100 тысяч
- slow: сейчас скрипт работает больше получаса
- pair-key: в следующей версии коллега хочет искать записи по паре значений и хранить каждый ключ как список Python из двух элементов, например `[a, b]`

## Нельзя раскрывать

- хэш
- хеш
- hash
- словар
- кортеж
- tuple
- frozenset

## Рубрика

- complexity-now: Оценена текущая сложность O(n · m): оператор `in` по списку просматривает элементы по очереди, и при 2·10^5 и 10^5 записях это порядка 10^10 сравнений
  + "in по списку — линейный проход, 200 тысяч раз по 100 тысяч — около 2·10^10 сравнений"
  - "скрипт медленный, потому что Python медленный" без оценки числа операций
- set-choice: Для второго набора выбрано множество `set` или ключи словаря `dict` с проверкой вхождения за O(1) в среднем
  - "отсортировать список и дальше проверять через in"
- hash-inside: Объяснено устройство хэш-таблицы: хэш ключа выбирает ячейку, коллизии разрешаются (в Python — открытой адресацией), при заполнении таблица расширяется; в худшем случае, когда у многих ключей совпадает ячейка, проверка деградирует до O(n)
- total-complexity: Названа итоговая сложность O(n + m) в среднем: построение множества за O(m) и n проверок по O(1)
- hashable-key: Объяснено, что список изменяем и не хэшируем, поэтому `set` и `dict` выдадут `TypeError: unhashable type`; ключ из пары значений нужно делать кортежем
  + "(a, b) можно положить в set, [a, b] — нет"
- dict-for-data: Для получения полей записи предложен словарь `dict`, где ключ — идентификатор, а значение — запись или нужные поля
