# Первая запись не раньше заданного момента

## Генерация

Придумай короткую легенду на материале: {domain}. Младший разработчик написал функцию, которая по заданному моменту времени находит первую запись не раньше этого момента, и просит коллегу посмотреть её. Саму функцию покажут кандидату отдельно после твоего текста: не пиши код, не пересказывай его и не оценивай. Расскажи, как устроены данные, кто и как часто вызывает функцию и что команда заметила при её работе

## Вопросы

Функция, которую прислали на проверку:

```python
def first_not_before(records, moment):
    lo, hi = 0, len(records) - 1
    while lo < hi:
        mid = (lo + hi) // 2
        if records[mid].time < moment:
            lo = mid
        else:
            hi = mid
    return lo
```

1. Почему здесь применим двоичный поиск? Какова его сложность по сравнению с перебором для этих данных?
2. Найдите ошибки в функции: на каких входах она не завершается или возвращает неверный ответ? Приведите конкретные примеры входов.
3. Исправьте функцию так, чтобы при одинаковом времени у нескольких записей она возвращала первую из них, а если подходящей записи нет, сообщала об этом. Как убедиться, что границы выбраны верно, и на каких входах вы её проверите?
4. Какая функция стандартной библиотеки Python решает эту задачу и чем отличаются её два варианта?

Ответ — развёрнутый текст на 10–20 предложений с исправленным кодом

## Факты

- sorted: записи упорядочены по времени по возрастанию
- size: записей около 10 миллионов, и функцию вызывают тысячи раз в минуту
- same-time: у нескольких записей подряд бывает одинаковое время
- later-moment: иногда запрашивают момент позже последней записи в списке
- hangs: на некоторых запросах функция не завершается, и программу приходится останавливать вручную

## Нельзя раскрывать

- bisect
- lower_bound
- mid + 1
- полуоткрыт
- инвариант
- зацикл
- бесконечн

## Рубрика

- sorted-precondition: Сказано, что двоичный поиск требует упорядоченности по ключу поиска, и названа сложность O(log n) против O(n) у перебора: для 10^7 записей это около 24 шагов вместо миллионов
- infinite-loop: Найдено зацикливание: при `lo = mid` и соседних `lo` и `hi` середина равна `lo`, и границы перестают сдвигаться; приведён пример входа
  + "время записей [1, 2], moment = 5: mid = 0, lo остаётся 0 навсегда"
  - "функция может зависнуть" без входа и механизма
- not-found: Найдено, что при `hi = len(records) - 1` функция не может сообщить об отсутствии подходящей записи: при моменте позже последней записи она вернёт последний индекс, а на пустом списке вернёт 0; предложено `hi = len(records)` и возврат `len(records)` или `None` как признак отсутствия
- fixed-code: Приведена исправленная функция: `lo, hi = 0, len(records)`, `lo = mid + 1` при `records[mid].time < moment`, иначе `hi = mid`; на одинаковом времени она возвращает первую подходящую запись
  + `while lo < hi: mid = (lo + hi) // 2; if a[mid] < x: lo = mid + 1 else: hi = mid`
  - исправление, которое находит какую-то запись с равным временем, но не первую
- bounds-check: Объяснено, почему границы верны: все записи левее `lo` раньше момента, все от `hi` и правее не раньше, и интервал сужается на каждом шаге; или перечислены краевые входы — пустой список, одна запись, все записи раньше, все не раньше, серия равных
- bisect: Назван `bisect.bisect_left` (с параметром `key` начиная с Python 3.10) и отличие от `bisect_right`: позиция левее или правее всех равных элементов
  + "bisect_left вернёт первую позицию с time >= moment, bisect_right — позицию после всех равных"
