# Ревью первой версии API

## Генерация

Придумай короткую легенду: команда сделала первую версию HTTP API для продукта "{domain}" и просит коллегу проверить его. Скажи, какие записи пользователя хранит сервис: в API они называются items. Само описание API покажут кандидату отдельно после твоего текста: не пиши адреса, методы и коды ответов, не пересказывай и не оценивай их. Опиши команду, клиентов API и ближайшие планы

## Вопросы

Описание API, которое команда прислала на проверку:

```text
GET  /api/getItems?userId=42      → 200 {"items": [ ...все записи пользователя... ]}
GET  /api/deleteItem?id=17        → 200 {"result": "ok"}
POST /api/updateItem              → 200 {"error": "item not found"}
POST /api/createItem              → 200 {"id": 18}
GET  /api/getItem?id=abc          → 500 Internal Server Error
```

1. Найдите проблемы этого API и объясните, к чему каждая приведёт для клиентов и для команды.
2. Предложите исправленный вариант: адреса, методы, коды ответов и формат ошибок. Как клиенту безопасно повторить запрос, на который он не дождался ответа?
3. Как менять API после выхода мобильного приложения, не ломая его старые версии?

Ответ — развёрнутый текст на 10–20 предложений, можно с примерами запросов

## Факты

- clients: API пользуются сайт и мобильное приложение
- release: через месяц мобильное приложение выходит в магазины приложений, и его старые версии останутся у пользователей надолго
- retries: у части пользователей нестабильная мобильная сеть, и приложение повторяет запрос, если не дождалось ответа
- monitoring: дежурный следит за долей ответов с ошибками по кодам ответа HTTP
- many-items: у активных пользователей накапливаются тысячи записей

## Нельзя раскрывать

- идемпотент
- 404
- 201
- 422
- RFC 7807
- problem+json
- пагинац
- постранич
- версионир
- /v1

## Рубрика

- resource-urls: Адреса построены вокруг ресурса, а действие задаёт метод: `GET /items`, `POST /items`, `PUT` или `PATCH /items/{id}`, `DELETE /items/{id}`
  - "переименовать getItems в get_items" без перехода к методам
- safe-get: Объяснено, что GET не должен менять данные: удаление через GET выполнят повторы запросов, предзагрузка ссылок браузером, прокси и поисковые роботы
- status-codes: Коды ответов отражают результат: 201 при создании, 404 для несуществующей записи, 400 или 422 для неверного `id`, а не 200 с полем `error` и не 500; мониторинг и клиент опираются на код
  + "updateItem отвечает 404, и дежурный видит ошибку в графике"
- error-format: Предложен единый формат тела ошибки, например JSON с машинным кодом и сообщением или RFC 7807 (problem+json)
- authz: Замечено, что `userId` в параметре позволяет запросить чужие записи; пользователь определяется по токену, а сервер проверяет права на каждую запись
- pagination: Список записей отдаётся постранично: `limit` и курсор или `offset`, а не все тысячи записей одним ответом
- retries: Учтены повторы клиента: `PUT` и `DELETE` можно повторять без вреда, а для создания нужен ключ идемпотентности или проверка дубликатов на сервере
  - "клиент не должен повторять запросы"
- versioning: Предложено версионирование API (`/v1/` в пути или заголовок) и обратно совместимые изменения: новые поля добавляются, старые не удаляются и не меняют смысл, пока живы старые версии приложения
