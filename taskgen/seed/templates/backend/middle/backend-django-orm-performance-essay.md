# Медленный эндпоинт на Django ORM

## Генерация

Опиши ситуацию: эндпоинт на Django REST Framework отдаёт {domain}, и пользователи жалуются, что страница грузится медленно. Приведи в блоках кода модели (3–4 класса), сериализатор и view из 8–15 строк. View получает записи простым вызовом `objects.filter(...)` с `order_by` по дате создания и больше ничего не делает с queryset. Сериализатор берёт поля связанных объектов и для каждого элемента вызывает `.count()` у связанных записей. Поля моделей объяви без дополнительных параметров базы данных. Код должен быть рабочим, без комментариев.

## Вопросы

1. Как вы будете искать причину медленной работы и какими инструментами?
2. Какие проблемы есть в приведённом коде? Покажите исправленный код.
3. Что нужно сделать на стороне базы данных?
4. Как проверить, что исправление помогло, и не допустить регресса в будущем?

Ответ — развёрнутый текст с фрагментами кода.

## Факты

- drf: эндпоинт сделан на Django REST Framework
- models: в коде есть модели Django, связанные через ForeignKey и через ManyToManyField
- view-filter: view получает записи главной модели вызовом objects.filter(...) и сортирует их по дате создания
- serializer-related: сериализатор для каждого элемента читает поля связанных объектов
- serializer-count: сериализатор для каждого элемента считает связанные записи вызовом .count()
- page-time: на странице 50 элементов, и эндпоинт отвечает около 3 секунд
- table-size: в таблице главной модели несколько миллионов строк

## Рубрика

- diagnose: Названы инструменты поиска причины: django-debug-toolbar, `connection.queries` или логирование SQL, `EXPLAIN ANALYZE`, профилировщик или APM
  + "в debug-toolbar видно 151 запрос вместо 3"
- n-plus-one: Названа проблема N+1: на каждый элемент страницы выполняются отдельные запросы за связанными объектами
- select-related: Для ForeignKey и OneToOne предложен `select_related`, который делает JOIN в одном запросе
  + `Order.objects.select_related("customer")`
  - `prefetch_related` для ForeignKey без объяснения разницы
- prefetch-related: Для ManyToMany и обратных связей предложен `prefetch_related`, при необходимости с `Prefetch` и отфильтрованным queryset; объяснено, что это отдельный запрос со склейкой в Python
- annotate-count: Подсчёт связанных записей перенесён в запрос через `annotate(Count(...))` вместо `.count()` в сериализаторе
  + `.annotate(items_count=Count("items"))`
- indexes: Предложен индекс под фильтр и сортировку, например составной `models.Index(fields=["status", "-created_at"])` через миграцию, и проверка плана запроса до и после
  - "добавим индекс на каждое поле"
- regression-guard: Предложен тест на число запросов (`assertNumQueries` или `django_assert_num_queries`) и замер времени до и после
- extras: Упомянуты дополнительные меры с оговорками: `only`/`defer` для тяжёлых полей, курсорная пагинация вместо OFFSET на больших таблицах, кэширование с инвалидацией
