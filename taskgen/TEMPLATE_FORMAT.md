# Формат шаблона задания

Шаблон — md-файл: YAML frontmatter и тело с разделами второго уровня. Сервис хранит файл целиком в БД, а поля frontmatter извлекает для фильтров. Модель, против которой проверяется разобранный шаблон, — `TemplateSpec` в `src/taskgen/contracts.py`

## Frontmatter

```yaml
---
name: algo-two-sum-sorted        # латиница, цифры и дефис; уникален в банке
description: >-                  # по этому тексту считается эмбеддинг для отбора
  Поиск пары элементов с заданной суммой в отсортированном массиве за линейное время
area: algo                       # код области из таблицы areas
grade: junior                    # код грейда из таблицы grades
skills: [python, two-pointers]   # коды навыков из таблицы skills
kind: code                       # code, essay или quiz
runtime: python                  # окружение песочницы, только для code
difficulty: 3                    # 1..10, единая шкала для всех грейдов
expected_minutes: 15
params:                          # значения выбирает код по seed, а не LLM
  n: {type: int, min: 1000, max: 5000}
  unique: {type: choice, choices: [true, false]}
scoring:                         # необязательно: переопределение весов балла
  weight_performance: 0.15
case_groups:                     # необязательно, только для code: группы тестовых кейсов
  manual: {weight: 2, required: true}
  random: {weight: 1}
  stress: {weight: 3, required: true}
---
```

`case_groups` делит кейсы задания на группы. Имя группы — строчная латиница, цифры, `_` и `-`. `weight` — доля группы в балле за тесты целиком, больше нуля: внутри группы кейсы равноценны, и число кейсов вес группы не меняет. `required: true` включает гейт: задание не решено, если упал хотя бы один кейс группы, каким бы ни был балл. `required: false` выключает гейт для группы, даже если её требует настройка `scoring.required_case_groups`; без `required` решает эта настройка, по умолчанию пустая. Веса и гейт не видны кандидату: они лежат в скрытых данных задания. Как группы входят в балл — [testing-mechanics.md](../docs/taskgen/testing-mechanics.md#балл-задания)

В банке принято деление по происхождению кейса: `manual` — кейсы, записанные в генераторе руками, с примерами из условия и границами; `random` — небольшие случайные кейсы, сверенные с перебором; `stress` — входы у верхней границы размера, на которых падает решение с неверной сложностью. Ручные и стрессовые кейсы обязательны, а случайные остаются зоной, где ошибку решает вес. Импорт отклоняет шаблон с кодом без обязательной группы: без гейта неверное решение, которое падает на одном кейсе из многих, набирает балл решённого. Что ещё импорт проверяет в песочнице — в разделе [Проверка при импорте](#проверка-при-импорте)

## Разделы тела

- `## Генерация` — инструкция для LLM: какую легенду придумать и что обязательно сказать в условии. Значения параметров подставляются в инструкцию как `{n}`, `{unique}`. У эссе LLM пишет по ней только ситуацию, без вопросов
- `## Вопросы` — только для `essay`, обязателен: текст задания, который идёт в условие дословно после ситуации; LLM его не видит и не меняет. Сюда же кладут неизменный материал к вопросам, например Dockerfile для ревью. Подстановки `{param}` работают так же, как в «Генерации»
- `## Факты` — только для `essay`, обязателен: список `- id: текст` с элементами сценария, на которые опирается рубрика. LLM обязана описать каждый факт в ситуации своими словами, а проверяльщик перед выдачей ищет в ситуации цитату на каждый факт. Факт пишется так, чтобы его можно было процитировать: присутствие, а не отсутствие («в Dockerfile нет USER» процитировать нечем). Подстановки `{param}` работают
- `## Нельзя раскрывать` — только для `essay` и `quiz`, по желанию автора, но рекомендуется: список `- фраза` с формулировками ответов, которых не должно быть в ситуации или кейсе. Поиск — подстрока после приведения к нижнему регистру, замены ё на е и пунктуации на пробелы; словоформы не сводятся, поэтому пишут общую часть слова: `утечк` найдёт «утечка» и «утечки». Фраза не должна встречаться в «Вопросах» или «Вопросе», в фактах и значениях параметров: иначе вопрос сам раскрывает ответ или шаблон не даст ни одного экземпляра, и разбор это отклоняет. В ответах задачки фраза встречаться может: ответы кандидат видит списком, а запрет действует на кейс, который не должен назвать верный ответ
- `## Вопрос` — только для `quiz`, обязателен: теоретический вопрос, который идёт в условие дословно после кейса; LLM его не видит. Подстановки `{param}` работают
- `## Варианты` — только для `quiz`, обязателен: варианты кейса, из которых seed задания выбирает один. Вариант начинается строкой `### id`, за ней блок `Факты:` со списком `- id: текст` и блок `Ответ:` со списком `+ верный ответ` и `- неверный ответ`. LLM пишет кейс только по фактам выбранного варианта, вопрос и ответы идут дословно, ответы — в порядке, перемешанном по seed. Требования разбора: не меньше двух вариантов, у каждого хотя бы один факт, ровно один верный ответ и не меньше трёх неверных без повторов, и хотя бы два варианта ведут к разным верным ответам: тогда утёкший ответ одного экземпляра не подходит к другому. Подстановки `{param}` работают в фактах и ответах

```markdown
## Варианты

### positive

Факты:
- weights: время проезда по каждой дороге — положительное число минут

Ответ:
+ Алгоритм Дейкстры
- Обход в ширину
- Алгоритм Беллмана — Форда
- Алгоритм Флойда — Уоршелла

### unit

Факты:
- weights: проезд по любой дороге занимает ровно одну минуту

Ответ:
+ Обход в ширину
- Алгоритм Дейкстры
- Алгоритм Беллмана — Форда
- Алгоритм Флойда — Уоршелла
```

Факты варианта обязаны однозначно вести к верному ответу и исключать каждый неверный: код этого не проверяет, а LLM-проверяльщик подтверждает только, что факты есть в кейсе. Лучше, когда у всех вариантов один набор ответов, а меняется только верный: тогда по набору ответов вариант не узнать

Seed выбирает вариант и значения параметров независимо друг от друга, а тема легенды из профиля кандидата не зависит ни от того, ни от другого. Поэтому факт варианта пишется общими словами, которые подходят к любому значению параметров шаблона: «объект», «запись», «числовое поле одной строки», «целевой класс», а не «пациент», «баланс счёта» или «мошенническая транзакция». Иначе модель сводит в один кейс два мира, например скоринг кредитов по визитам пациентов. Назвать объект словами домена — работа модели, а автор проверяет, что при каждом значении параметров факты остаются правдоподобными и ведут к тому же ответу. Код этого не проверяет. Зависимость домена от варианта не вводится: тогда домен подсказывал бы вариант, а с ним и верный ответ
- `## Решения` — только для `code`, обязателен: размеченные решения задачи. Решение начинается строкой `### id +` (верное) или `### id -` (заведомо неверное), под ней — необязательное пояснение текстом и ровно один блок кода. Нужно хотя бы одно верное и хотя бы одно неверное решение. Каждое решение определяет функцию из `## Сигнатура`; у Python это функция верхнего уровня без синтаксических ошибок. Первое верное решение — мерило: его прогон проверяет каждый экземпляр при генерации и задаёт скорость для балла производительности. Остальные верные решения нужны, например, для честного медленного решения: импорт проверяет, что оно укладывается в лимиты. Неверное решение воспроизводит правдоподобную ошибку кандидата, а не синтаксическую: тесты обязаны её поймать. Решения — скрытые данные: ни кандидат, ни LLM их не видят. Если в коде есть строка из трёх обратных кавычек, блок открывают четырьмя

````markdown
## Решения

### reference +

```python
def count_pairs(values, limit):
    ...
```

### strict-limit -

Строгое сравнение с порогом

```python
def count_pairs(values, limit):
    ...
```
````

- `## Сигнатура` — только для `code`: имя функции, которую пишет кандидат, одной строкой в блоке кода
- `## Тесты` — только для `code`: блок кода на Python с функцией `generate(params, rng)`, которая возвращает список пар `{"input": ..., "expected": ...}`. Ожидаемые значения сервис перепроверяет верными решениями в песочнице. Что может быть в `input` и `expected`, задаёт протокол драйвера в `src/taskgen/sandbox/protocol.py`, а какие типы принимает функция на C++ — заголовок `src/taskgen/sandbox/drivers/taskgen_driver.cpp`. Если шаблон объявил `case_groups`, у каждого кейса есть поле `"group"` с именем объявленной группы, а у обязательной группы есть хотя бы один кейс; иначе экземпляр не собирается. Первые кейсы списка кандидат видит примерами, но только вход и ответ, без группы
- `## Рубрика` — для `code` и `essay`, обязательна; у `quiz` её нет, ответ сверяется с ключом. Список пунктов `- id: текст`. Под пунктом могут идти вложенные строки `+ пример, который проходит` и `- пример, который не проходит`

## Проверка при импорте

Импорт (`taskgen import`, `POST /templates`, `POST /templates/bulk`) сначала разбирает шаблон по правилам выше и сверяет области, грейды и навыки со справочниками. Шаблон с кодом затем проходит проверку в песочнице — код в [src/taskgen/bank/validation.py](src/taskgen/bank/validation.py). На каждом seed от 0 до `import_check.seeds − 1` генератор запускается так же, как при генерации экземпляра, и:

- даёт не меньше `MIN_CASES` кейсов, не все с одним ответом, входы — массивы аргументов, а все входы вместе не больше `MAX_INPUT_BYTES`; обе константы заданы в `validation.py`;
- каждое верное решение проходит все кейсы в лимитах `sandbox.run_timeout_ms` и `sandbox.run_memory_limit_bytes`;
- каждое неверное решение компилируется и не решено даже при идеальных рубрике, качестве и скорости: это строже, чем «проваливает хотя бы один кейс», потому что провал в необязательной группе может оставить балл выше порога;
- решения-константы, которые возвращают ответ первого кейса или пустое значение и не смотрят на вход, тоже не решены.

Каждая проблема называет файл, seed и причину: какое решение, какие кейсы, какой генератор упал и с какими параметрами. Проблемы всех файлов набора выводятся сразу, а в БД не пишется ничего. Если песочница недоступна, импорт шаблонов с кодом не проходит молча, а завершается ошибкой: `taskgen import` — кодом 3, API — ответом 503. Шаблонам без кода песочница не нужна
