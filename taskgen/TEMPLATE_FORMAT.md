# Формат шаблона задания

Шаблон — md-файл: YAML frontmatter и тело с разделами второго уровня. Сервис хранит файл целиком в БД, а поля frontmatter извлекает для фильтров. Модель, против которой проверяется разобранный шаблон, — `TemplateSpec` в `src/taskgen/contracts.py`

## Frontmatter

```yaml
---
name: algo-two-sum-sorted        # латиница, цифры и дефис; уникален в банке
description: >-                  # по этому тексту считается эмбеддинг для отбора
  Поиск пары элементов с заданной суммой в отсортированном массиве за линейное время
area: algo                       # код области из таблицы areas
grade: junior                    # код грейда из таблицы grades
skills: [python, two-pointers]   # коды навыков из таблицы skills
kind: code                       # code, essay или quiz
runtime: python                  # окружение песочницы, только для code
io: function                     # только для code: function или stdio
check: json                      # необязательно, только для code: режим проверки ответа
difficulty: 3                    # 1..10, единая шкала для всех грейдов
expected_minutes: 15
params:                          # значения выбирает код по seed, а не LLM
  n: {type: int, min: 1000, max: 5000}
  unique: {type: choice, choices: [true, false]}
scoring:                         # необязательно: переопределение весов балла
  weight_performance: 0.15
case_groups:                     # необязательно, только для code: группы тестовых кейсов
  manual: {weight: 2, required: true}
  random: {weight: 1}
  stress: {weight: 3, required: true}
---
```

`runtime` — имя окружения из [runtimes.yaml](src/taskgen/sandbox/runtimes.yaml), в котором решают задания; служебное окружение `analyzers` не подходит. Список окружений сервис читает из этого файла при старте, вместе с шаблонами окружения не загружаются. `runtime` задаёт окружение, а язык его кода записан в поле `code` той же записи реестра: у `python-ml` это `python`

`io` обязательно для задания с кодом и задаёт, что пишет кандидат. `function` — функцию из раздела «Сигнатура»: драйвер языка вызывает её на аргументах кейса. `stdio` — программу целиком: она читает вход из stdin и из файлов рядом с собой и печатает ответ в stdout. Задачу stdio можно писать на любом окружении из [runtimes.yaml](src/taskgen/sandbox/runtimes.yaml), задачу-функцию — только на окружении, для языка `code` которого написан драйвер, сейчас это Python и C++; иначе разбор шаблона отклоняет `io: function`. `check` выбирает режим проверки ответа, описанный в разделе [Проверка ответа](#проверка-ответа); без поля это `json` для `function` и `tokens` для `stdio`

`case_groups` делит кейсы задания на группы. Имя группы — строчная латиница, цифры, `_` и `-`. `weight` — доля группы в балле за тесты целиком, больше нуля: внутри группы кейсы равноценны, и число кейсов вес группы не меняет. `required: true` включает гейт: задание не решено, если упал хотя бы один кейс группы, каким бы ни был балл. `required: false` выключает гейт для группы, даже если её требует настройка `scoring.required_case_groups`; без `required` решает эта настройка, по умолчанию пустая. Веса и гейт не видны кандидату: они лежат в скрытых данных задания. Как группы входят в балл — [testing-mechanics.md](../docs/taskgen/testing-mechanics.md#балл-задания)

В банке принято деление по происхождению кейса: `manual` — кейсы, записанные в генераторе руками, с примерами из условия и границами; `random` — небольшие случайные кейсы, сверенные с перебором; `stress` — входы у верхней границы размера, на которых падает решение с неверной сложностью. Ручные и стрессовые кейсы обязательны, а случайные остаются зоной, где ошибку решает вес. Импорт отклоняет шаблон с кодом без обязательной группы: без гейта неверное решение, которое падает на одном кейсе из многих, набирает балл решённого. Что ещё импорт проверяет в песочнице — в разделе [Проверка при импорте](#проверка-при-импорте)

## Разделы тела

Тело разбирается как Markdown по правилам CommonMark (библиотека markdown-it-py, обёртка — [markdown.py](src/taskgen/markdown.py)). Поэтому разбор видит те же блоки кода и заголовки, что и отрисованный файл. Заголовок `##` начинает раздел, `###` — запись внутри раздела, а заголовок внутри блока кода, списка или цитаты заголовком не считается. Строка `---` под абзацем по CommonMark превращает абзац в заголовок второго уровня, и разбор тоже примет его за раздел. Разделитель между абзацами отделяют от текста пустой строкой

- `## Генерация` — инструкция для LLM: какую легенду придумать и что обязательно сказать в условии. Значения параметров подставляются в инструкцию как `{n}`, `{unique}`. У эссе LLM пишет по ней только ситуацию, без вопросов
- `## Вопросы` — только для `essay`, обязателен: текст задания, который идёт в условие дословно после ситуации; LLM его не видит и не меняет. Сюда же кладут неизменный материал к вопросам, например Dockerfile для ревью. Подстановки `{param}` работают так же, как в «Генерации»
- `## Факты` — только для `essay`, обязателен: список `- id: текст` с элементами сценария, на которые опирается рубрика. LLM обязана описать каждый факт в ситуации своими словами, а проверяльщик перед выдачей ищет в ситуации подтверждение каждого факта: цитату или предложение. Факт пишется так, чтобы на него можно было указать в тексте: присутствие, а не отсутствие («в Dockerfile нет USER» подтвердить нечем). Подстановки `{param}` работают
- `## Нельзя раскрывать` — только для `essay` и `quiz`, по желанию автора, но рекомендуется: список `- фраза` с формулировками ответов, которых не должно быть в ситуации или кейсе. Поиск — подстрока после приведения к нижнему регистру, замены ё на е и пунктуации на пробелы; словоформы не сводятся, поэтому пишут общую часть слова: `утечк` найдёт «утечка» и «утечки». Фраза не должна встречаться в «Вопросах» или «Вопросе», в фактах и значениях параметров: иначе вопрос сам раскрывает ответ или шаблон не даст ни одного экземпляра, и разбор это отклоняет. В ответах задачки фраза встречаться может: ответы кандидат видит списком, а запрет действует на кейс, который не должен назвать верный ответ
- `## Вопрос` — только для `quiz`, обязателен: теоретический вопрос, который идёт в условие дословно после кейса; LLM его не видит. Подстановки `{param}` работают
- `## Варианты` — только для `quiz`, обязателен: варианты кейса, из которых seed задания выбирает один. Вариант начинается строкой `### id`, за ней блок `Факты:` со списком `- id: текст` и блок `Ответ:` со списком `+ верный ответ` и `- неверный ответ`. LLM пишет кейс только по фактам выбранного варианта, вопрос и ответы идут дословно, ответы — в порядке, перемешанном по seed. Требования разбора: не меньше двух вариантов, у каждого хотя бы один факт, ровно один верный ответ и не меньше трёх неверных без повторов, и хотя бы два варианта ведут к разным верным ответам: тогда утёкший ответ одного экземпляра не подходит к другому. Подстановки `{param}` работают в фактах и ответах

```markdown
## Варианты

### positive

Факты:
- weights: время проезда по каждой дороге — положительное число минут

Ответ:
+ Алгоритм Дейкстры
- Обход в ширину
- Алгоритм Беллмана — Форда
- Алгоритм Флойда — Уоршелла

### unit

Факты:
- weights: проезд по любой дороге занимает ровно одну минуту

Ответ:
+ Обход в ширину
- Алгоритм Дейкстры
- Алгоритм Беллмана — Форда
- Алгоритм Флойда — Уоршелла
```

Факты варианта обязаны однозначно вести к верному ответу и исключать каждый неверный: код этого не проверяет, а LLM-проверяльщик подтверждает только, что факты есть в кейсе. Лучше, когда у всех вариантов один набор ответов, а меняется только верный: тогда по набору ответов вариант не узнать

Seed выбирает вариант и значения параметров независимо друг от друга, а тема легенды из профиля кандидата не зависит ни от того, ни от другого. Поэтому факт варианта пишется общими словами, которые подходят к любому значению параметров шаблона: «объект», «запись», «числовое поле одной строки», «целевой класс», а не «пациент», «баланс счёта» или «мошенническая транзакция». Иначе модель сводит в один кейс два мира, например скоринг кредитов по визитам пациентов. Назвать объект словами домена — работа модели, а автор проверяет, что при каждом значении параметров факты остаются правдоподобными и ведут к тому же ответу. Код этого не проверяет. Зависимость домена от варианта не вводится: тогда домен подсказывал бы вариант, а с ним и верный ответ
- `## Решения` — только для `code`, обязателен: размеченные решения задачи. Решение начинается строкой `### id +` (верное) или `### id -` (заведомо неверное), под ней — необязательное пояснение текстом и ровно один блок кода. Метка блока, то есть слово после открывающих кавычек, обязательна и называет язык окружения `runtime`: `python` у `python` и `python-ml`, `cpp` или `c++` у `cpp`, `bash` у `bash`. Метка другого языка или имя окружения вроде `python-ml` — ошибка разбора. Нужно хотя бы одно верное и хотя бы одно неверное решение. У `io: function` каждое решение определяет функцию из `## Сигнатура`; у Python это функция верхнего уровня. У `io: stdio` решение — программа целиком. Код на Python, в том числе у окружения `python-ml`, не должен содержать синтаксических ошибок. Первое верное решение — мерило: его прогон проверяет каждый экземпляр при генерации и задаёт скорость для балла производительности. Остальные верные решения нужны, например, для честного медленного решения: импорт проверяет, что оно укладывается в лимиты. Неверное решение воспроизводит правдоподобную ошибку кандидата, а не синтаксическую: тесты обязаны её поймать. Решения — скрытые данные: ни кандидат, ни LLM их не видят. Если в коде есть строка из трёх обратных кавычек, блок открывают четырьмя

````markdown
## Решения

### reference +

```python
def count_pairs(values, limit):
    ...
```

### strict-limit -

Строгое сравнение с порогом

```python
def count_pairs(values, limit):
    ...
```
````

- `## Сигнатура` — только для `io: function`, обязательна: имя функции, которую пишет кандидат, одной строкой в блоке кода. У `io: stdio` раздела нет
- `## Проверяльщик` — только для `check: checker`, обязателен: свой проверяльщик шаблона, ровно один блок кода. Метка блока называет окружение из реестра, в котором проверяльщик запускается, например `python`: в отличие от решений, проверяльщик не обязан работать в окружении задания. Контракт программы — в разделе [Проверка ответа](#проверка-ответа)
- `## Тесты` — только для `code`: блок кода с меткой `python` и функцией `generate(params, rng)`, которая возвращает список кейсов. Кейс `io: function` — `{"input": [аргументы], "expected": значение}`; что может быть в них, задаёт протокол драйвера в `src/taskgen/sandbox/protocol.py`, а какие типы принимает функция на C++ — заголовок `src/taskgen/sandbox/drivers/taskgen_driver.cpp`. Кейс `io: stdio` — `{"stdin": "текст", "expected": "ожидаемый вывод"}` и необязательное поле `"files": {"имя": "текст"}`: файлы лежат в каталоге программы. Имя файла — одно имя без каталогов, не скрытое; C++ файлов данных не принимает, потому что пакет gcc собирает каждый файл запуска как исходник. Ожидаемые значения сервис перепроверяет верными решениями в песочнице. Если шаблон объявил `case_groups`, у каждого кейса есть поле `"group"` с именем объявленной группы, а у обязательной группы есть хотя бы один кейс; иначе экземпляр не собирается. Первые кейсы списка кандидат видит примерами, но только вход и ответ, без группы
- `## Рубрика` — для `code` и `essay`, обязательна; у `quiz` её нет, ответ сверяется с ключом. Список пунктов `- id: текст`. Под пунктом могут идти вложенные строки `+ пример, который проходит` и `- пример, который не проходит`

## Проверка ответа

Ответ кейса сверяется с `expected` в режиме `check`. Встроенные режимы работают в сервисе, код — [src/taskgen/sandbox/checkers.py](src/taskgen/sandbox/checkers.py):

| Режим | Как сравнивает | Вид io |
|---|---|---|
| `tokens` | вывод и ожидаемое режутся по пробелам и переводам строк, части равны попарно | `stdio` |
| `exact` | строки равны побайтно, с пробелами и переводами строк | `stdio` |
| `float` | как `tokens`, но части-числа сравниваются с допуском | `stdio` |
| `json` | оба текста разбираются как JSON; числа с плавающей точкой — с допуском | `function`, `stdio` |
| `checker` | свой проверяльщик шаблона в песочнице | `function`, `stdio` |

Ответ функции драйвер печатает как JSON, поэтому у `io: function` текстовые режимы не принимаются. Допуск чисел задан в `checkers.py` один раз для `float` и `json`

Свой проверяльщик нужен, когда верных ответов несколько: любой порядок, любой кратчайший путь. Это программа на любом окружении реестра, которое принимает файлы данных, и она исполняется в песочнице, а не в сервисе. Рядом с ней лежат `input.txt` — вход кейса (stdin у `stdio`, JSON аргументов у `function`), `output.txt` — ответ решения, `answer.txt` — `expected` (у `function` это JSON) и файлы кейса `stdio`. Те же три имени приходят аргументами в порядке testlib. Код выхода 0 — ответ верен, 1 — неверен. Другой код, сигнал или лимит — отказ самого проверяльщика: кейс не засчитан, а импорт называет это дефектом шаблона. Решение кандидата файла `answer.txt` не видит: проверяльщик запускается отдельно, после решения. Ответ длиннее 64 КиБ проверяльщику не передаётся, и кейс не засчитан

````markdown
## Проверяльщик

```python
import sys

_, output, answer = (open(name, encoding="utf-8").read().split() for name in sys.argv[1:4])
sys.exit(0 if sorted(output) == sorted(answer) else 1)
```
````

## Проверка при импорте

Импорт (`taskgen import`, `POST /templates`, `POST /templates/bulk`) сначала разбирает шаблон по правилам выше и сверяет области, грейды и навыки со справочниками. Шаблон с кодом затем проходит проверку в песочнице — код в [src/taskgen/bank/validation.py](src/taskgen/bank/validation.py). На каждом seed от 0 до `import_check.seeds − 1` генератор запускается так же, как при генерации экземпляра, и проверяется следующее:

- генератор даёт не меньше `MIN_CASES` кейсов, и не все они ждут один ответ; у `stdio` ответы, равные в режиме проверки, считаются одним, например `0` и `0\n` для `tokens`
- у `function` входы — массивы аргументов, и все входы вместе не больше `MAX_INPUT_BYTES`; у `stdio` этот предел действует на stdin, файлы и ответ каждого кейса отдельно. Обе константы заданы в `validation.py`
- каждое верное решение проходит все кейсы в лимитах `sandbox.run_timeout_ms` и `sandbox.run_memory_limit_bytes`
- каждое неверное решение компилируется и не решено даже при идеальных рубрике, качестве и скорости: это строже, чем «проваливает хотя бы один кейс», потому что провал в необязательной группе может оставить балл выше порога
- решения-константы, которые возвращают ответ первого кейса или пустое значение и не смотрят на вход, тоже не решены; у `stdio` такая программа пишется на Python, потому что проверяется только её вывод
- свой проверяльщик не отказывает ни на одном решении: неверное решение должно быть поймано ответом «неверно», а не падением проверяльщика

Каждая проблема называет файл, seed и причину: какое решение, какие кейсы, какой генератор упал и с какими параметрами. Проблемы всех файлов набора выводятся сразу, а в БД не пишется ничего. Если песочница недоступна, импорт шаблонов с кодом не проходит молча, а завершается ошибкой: `taskgen import` — кодом 3, API — ответом 503. Шаблонам без кода песочница не нужна
