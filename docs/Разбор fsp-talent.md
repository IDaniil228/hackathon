# Разбор решения fsp-talent

Разбор публичного репозитория [SergeLyamin/fsp-talent](https://github.com/SergeLyamin/fsp-talent) на коммите `3965f65` от 5 октября 2026 года. Это решение того же специального трека. Документ собирает идеи, которые имеет смысл взять в нашу платформу, и ошибки, которые не стоит повторять

> [!WARNING]
> В репозитории нет файла лицензии, поэтому все права на код принадлежат авторам. Берём идеи и механизмы, код не копируем

Выводы ниже сделаны по чтению кода и документации репозитория. Их код мы не запускали

## Что у них есть

Монолит на FastAPI и SQLAlchemy, фронтенд на React. Сайт развёрнут на собственном домене, есть демо-аккаунты и CI. Путь продукта: кандидат проходит опрос и адаптивный тест, получает категорию "специализация + грейд", работодатель описывает потребность, получает подборку с объяснением и сам отправляет приглашение с зарплатой

| Часть | Как сделано |
|---|---|
| Тестирование | Около 130 параметризованных шаблонов-функций, модель IRT 3PL, адаптивный тест (CAT) на 10–18 заданий с ответом вариантом или числом |
| Подбор | Правила и словари без ML: разбор текста вакансии, множитель категории, взвешенная сумма факторов, строка объяснения на каждый фактор |
| Контакт | Приглашение с обязательной вилкой зарплаты, статусы, письма, контакты открываются после принятия |
| LLM | Только помощник по сайту на GigaChat с запасными сценариями без модели |

Что у нас по тем же частям: тестирование — сервис `taskgen` ([docs/taskgen](taskgen/README.md)), подбор спроектирован в разделе `match` [структуры БД](Структура%20БД.md), основного бэкенда и фронтенда пока нет

## Подбор: что взять

Их оценка кандидата под потребность — произведение множителя категории на взвешенное среднее факторов. Наш проект конвейера — префильтр, векторная близость, затем LLM ([Структура БД.md](Структура%20БД.md), раздел "Конвейер подбора"). Идеи ниже встраиваются в этот конвейер, а не заменяют его

### Детерминированные факторы до LLM

Каждый кандидат получает разложение по факторам и строки объяснения трёх видов: плюс, минус и нейтральная справка. Примеры строк: "Нет в стеке: Kafka", "Ожидания выше бюджета на 12%", "лучше 70% кандидатов категории"

Для нас это слой между вектором и LLM. Разложение сохраняется в `match.search_results`, а LLM пишет `explanation` по этим фактам, а не по догадке. Так же устроен наш machine summary: факты, текст, проверка текста по фактам ([testing-mechanics.md](taskgen/testing-mechanics.md#machine-summary)). Для разложения в `search_results` понадобится поле `jsonb`

Факторы, которые у них есть:

- результат теста как положение внутри грейда: 0 на пороге своего грейда, 1 на пороге следующего. У нас этому соответствует общий балл сессии `taskgen`
- процентиль результата среди кандидатов той же категории. Считается по всей категории до уточняющих фильтров, чтобы фильтр не менял процентиль
- покрытие стека: совпадение даёт 1, близкая технология 0.5 (MySQL вместо PostgreSQL), обязательные навыки весят больше желательных
- достижения ФСП: место, уровень соревнования, давность и связь дисциплины со специализацией
- условия: матрица совместимости форматов работы и ступенчатая оценка зарплатных ожиданий относительно бюджета
- свежесть подтверждения грейда

### Категория как множитель

Пул подборки — точная категория, соседний грейд и смежные специализации по таблице смежности. Множитель 1 для точной категории и меньше для соседних. Рядом с подборкой работодатель видит список рекомендуемых категорий с числом кандидатов в каждой и пояснением вида "грейд выше: сильнее, но дороже"

Для нас таблица смежности специализаций — кандидат в справочник `ref`, а не константа в коде

### Уточнение без потери подборки

Фильтр применяется поверх готовой подборки, ответ несёт оба размера: сколько было и сколько осталось. Это дешёвая форма требования ТЗ для фильтров кнопкой. Новый `search_runs` с `parent_run_id` остаётся для уточнения репликой в чате

### Разбор текста вакансии

Словарь синонимов технологий, маркеры желательных требований ("будет плюсом"), слова грейда или требуемый опыт в годах, регулярные выражения для вилки. Каждое решение разбора записывается заметкой: "специализация определена по словам X и Y", и работодатель правит поля до сохранения

Нам основной путь — LLM со структурированным выводом. Словарный разбор подходит как запасной путь при недоступной модели. Тот же словарь синонимов нормализует навыки кандидата, поэтому совпадения считаются одинаково с обеих сторон. У нас эту роль играет `ref.skill_aliases`

## Подбор: что не повторять

- **Фактор, который выпадает не у всех.** У них сходство описаний считается, только если у кандидата заполнено поле "о себе". Пустое поле убирает фактор из нормировки, а заполненное без совпадений даёт 0. Кандидат, который написал о себе, проигрывает тому, кто не написал. Правило: применимость фактора определяет запрос, а не профиль кандидата. Нет данных у кандидата — нейтральное значение, а не исключение фактора
- **Расхождение комментария и кода.** Комментарий говорит, что отсутствие достижений ФСП не штрафуется, а фактор с весом 0.2 есть у всех и даёт 0. Решение "штрафовать или нет" надо принять явно и записать в одном месте
- **Веса без валидации.** Веса факторов заданы экспертно, проверка точности подбора (precision@k на синтетических парах "вакансия — кандидат") у них в плане, но не сделана. ТЗ требует процедуру валидации и результаты. Нам нужен такой набор пар до выбора весов
- **Сходство текстов по префиксам слов.** Общие шестибуквенные основы плохо ловят смысл. У нас для этого эмбеддинги

## Тестирование: что можно извлечь

Их тест короче и мерит распознавание: кандидат читает код и выбирает ответ, но код не пишет. Наш тест мерит практический навык, но дольше и опирается на LLM-судью ([testing-mechanics.md](taskgen/testing-mechanics.md)). Сама модель заданий у нас сильнее, но несколько механизмов вокруг неё стоит взять

- **Общая шкала уровня.** IRT кладёт сложность заданий и уровень кандидатов на одну шкалу, и результаты кандидатов с разными наборами заданий сравнимы. Нам такая шкала нужна для фактора теста в подборе. Вариант для нас — модель для баллов от 0 до 1 (graded response model) по ответам пилота. До пилота данных для калибровки нет, поэтому это пункт [процедуры на пилотных данных](taskgen/validation.md#процедура-на-пилотных-данных)
- **Дрейф решаемости как детектор утечки.** Если доля решивших шаблон растёт сильнее, чем предсказывает уровень кандидатов, шаблон помечается и снимается с выдачи. Уровень для сравнения считается только по заданиям, ответ на которые утечь не может. У нас это ложится на `item_analysis.sql`: решаемость шаблона по времени против балла по остальным заданиям сессии
- **Валидация симуляцией.** Синтетические кандидаты с известным уровнем проходят тест, и по ним считаются точность грейда, согласованность при повторе и устойчивость к атаке утечкой. Это даёт числа для раздела валидации до появления реальных кандидатов
- **Доля заданий, которые можно выучить.** У них концептуальных вопросов не больше 30% теста, и их вес в оценке ниже. У нас похожую роль играет малый вес блока задачек; ограничение доли в составе теста можно добавить в `test_configs`
- **Досрочная остановка при уверенном решении.** Для нашего формата заданий в часы это не подходит целиком, но для блока задачек применимо
- **Превью проверки под вакансию.** Работодатель видит план теста под свою потребность: темы, их доли и два экземпляра одного шаблона с разными данными. Это наглядно показывает жюри устойчивость к распространению. У нас то же даёт объяснение отбора `GET /sessions/{id}/selection` плюс два экземпляра одного шаблона

## Продукт и контакт: что взять

Механика выхода на контакт — главный критерий ТЗ. У них она полностью готова, и правила стоит сверить с нашей схемой `hire`

- одно активное приглашение от работодателя одному кандидату
- вилка зарплаты обязательна, и нижняя граница не больше верхней
- без названия компании пригласить нельзя
- имя кандидата скрыто по умолчанию, контакты открываются после принятия приглашения
- приглашение ссылается на потребность, поэтому у потребности есть воронка: отправлено, просмотрено, принято, отклонено
- избранное кандидатов в рамках одной потребности
- в поиске только кандидаты с согласием на публикацию и подтверждённым грейдом
- согласия хранятся отдельной таблицей с версией документа и датой отзыва. У нас это `core.user_consents`
- ограничение частоты: повтор теста не раньше чем через неделю, смена категории не чаще раза в 90 дней, не больше трёх попыток в сутки. У нас ограничение частоты смены грейда держит основной бэкенд, и значения надо выбрать
- интерфейс провайдера данных ФСП с заглушкой: платформа работает без реального API ФСП, а подключение меняет только реализацию

## Подача для жюри

- сайт на домене и демо-аккаунты на каждую роль: пустой кандидат для показа пути "опрос → тест → категория" и десятки синтетических кандидатов с пройденным тестом
- помощник по сайту знает карту разделов по ролям и отбрасывает ссылки, которых нет в карте. Без ключа модели он отвечает готовыми сценариями
- CI проверяет тесты, сборку фронтенда и запуск всего стека в Docker с проверкой health-эндпоинта
