# Хранение данных Сцепки

PostgreSQL с pgvector хранит предметные данные платформы. Сервер запускается из [db/docker-compose.yml](../db/docker-compose.yml), модели находятся в `api/app/db/models`, миграции — в `api/migrations/versions`

[Предметная схема](Структура%20БД.md) описывает таблицы и связи. Для запуска и выдачи runtime-прав используйте [инструкцию API](api/deployment.md); для дополнительной роли сервиса подбора — [инструкцию matcher](matcher/deployment.md)

## Подготовка и обслуживание

`fspdb seed` наполняет справочники, `relevance` пересчитывает веса навыков, `stats` показывает состав базы. Режимы `seed-demo` и требования к Faker описаны в [инструкции Сцепки](frontend/development.md#демоданные)

Миграции применяет роль подготовки. Runtime API управляет аккаунтами, профилями и наймом, а `match` читает с исключением приватных снимков карт. matcher читает разрешённые данные профилей и пишет таблицы подбора

Приложение обновляет служебные даты и меняет текущую категорию транзакционно. Общая функция `profile.lock_candidate` синхронизирует изменения приватности с сохранением геометрии; её определяет миграция карт, а не отдельная копия SQL в сервисах

## Выгрузки

`fspdb dump-schema` собирает представление таблиц из моделей, `dump-data` выгружает содержимое. Это материалы для просмотра и переноса данных, не замена миграциям: ORM-выгрузка не включает произвольные функции из миграций

Для восстановления рабочего приложения сначала примените полный набор миграций к отдельной пустой базе, затем восстановите данные и выдайте runtime-права. Проверяйте состояние Alembic и реальные права ролей после восстановления

## Проверки

`alembic check` сравнивает модели с базой, но не доказывает работоспособность функций, ролей и внешних сервисов. Их проверяют интеграционные тесты API и matcher по инструкциям соответствующих компонентов
