# Сборка, развёртывание и локальный запуск matcher

Команды выполняются из каталога `matcher/`, если не сказано иное. Состав контейнеров и порты задаёт [docker-compose.yml](../../matcher/docker-compose.yml), настройки сервиса и их переменные окружения — [generated/settings.md](generated/settings.md), версии компонентов — [generated/libraries.md](generated/libraries.md)

Неизвестная переменная внутри раздела настроек, например опечатка в `MATCHER_LLM__RANKER__MODEL`, останавливает старт с ошибкой, которая называет поле. Переменные без раздела сервис не проверяет: файл `.env` читает ещё и compose, и в нём бывают чужие переменные

## Что нужно

- Docker с Compose v2. [uv](https://docs.astral.sh/uv/) нужен для команд разработки и тестов
- База api с применёнными миграциями. matcher не создаёт схему `match`, а использует её: таблицы подбора принадлежат api ([architecture.md](architecture.md#данные-одна-база-с-api))
- OpenAI-совместимый провайдер для эмбеддингов. Без него подбор работает только на пуле не больше `vector.top_k`, см. [matching-mechanics.md](matching-mechanics.md#что-происходит-без-части-служб). Провайдер и модель каждой роли задают настройки группы `llm`, умолчания — в [generated/settings.md](generated/settings.md#llm)
- Для LLM-стадии: провайдеры моделей переписчика, ранжировщика и проверяльщика. LLM-стадия по умолчанию выключена

## 1. Настройки

Создайте `matcher/.env`: его читает и сервис в контейнере, и сервис, запущенный на хосте. Файл в `.gitignore`, ключи не попадут в репозиторий:

```sh
echo "MATCHER_BOOTSTRAP_ADMIN_KEY=$(openssl rand -hex 32)" > .env
```

Этот ключ — первый ключ роли `admin`. Остальные ключи выпускает `POST /keys`, и сервис хранит их только хэшем

Чтобы включить LLM-стадию, добавьте `MATCHER_LLM_STAGE__ENABLED=true` и ключ облачного провайдера, если роли используют его. Ключ провайдера задаётся только переменной окружения вида `MATCHER_LLM__PROVIDERS__<ИМЯ>__API_KEY`; без ключа сервис стартует и пишет предупреждение в журнал, а вызов роли этого провайдера завершается ошибкой, и стадия выпадает ([matching-mechanics.md](matching-mechanics.md#что-происходит-без-части-служб))

Чтобы карточки получали machine summary, укажите ключ роли `client` в taskgen: `MATCHER_TASKGEN__API_KEY`. Адрес taskgen в compose уже задан по имени сервиса, вне compose — `MATCHER_TASKGEN__BASE_URL`

### Локальные модели и облако

Роль называет модель строкой `провайдер/модель`, как в [taskgen](../taskgen/deployment.md#другие-провайдеры-и-полностью-локальный-режим): роль переезжает к другому провайдеру переменной окружения. Ollama на хосте контейнер достаёт через `host.docker.internal`; Ollama по умолчанию слушает только `127.0.0.1`, поэтому её запускают с `OLLAMA_HOST=0.0.0.0:11434`. Модель эмбеддингов по умолчанию загружается так:

```sh
ollama pull bge-m3
```

Облачный провайдер получает тексты карточек кандидатов и потребностей, и если в них есть персональные данные, передача требует отдельного разбора на соответствие 152-ФЗ ([security.md](security.md#что-остаётся-открытым)). Полностью локальный режим — переназначить облачные роли на модель Ollama переменными `MATCHER_LLM__RANKER__MODEL` и `MATCHER_LLM__CHECKER__MODEL`

## 2. Контейнеры

В составе платформы сервис поднимается вместе с остальными из корня репозитория:

```sh
cp -n .env.example .env
docker compose up -d --build
docker compose exec api fspdb seed
docker compose exec api fspdb seed-demo
docker compose exec api fspdb relevance
```

Корневой `docker-compose.yml` подключает compose сервиса через `include`, и matcher достаёт api и taskgen по именам сети. Сервис слушает на хосте порт 8002: 8000 занимает api, а 8001 — taskgen. Внутри сети Compose это `matcher:8000`

Порядок запуска важен. Роль `matcher` и её права создаёт одноразовый контейнер `matcher-db-init` по [db-init.sql](../../matcher/db-init.sql), а сам сервис ждёт его завершения. Контейнер ждёт, пока миграции api создадут схему `match`, и только тогда выдаёт права, потому что права на существующие таблицы выдаются в момент запуска, а на будущие — правилами по умолчанию для роли-владельца таблиц api. Если схема не появилась за `MATCHER_WAIT_SECONDS`, контейнер завершается ошибкой с сообщением, что миграции api не выполнены. Контейнер идемпотентен и запускается при каждом старте

Сервис при старте применяет собственные миграции (`alembic upgrade head`): они создают таблицу ключей в схеме `matcher`. Затем он сверяет размерность вектора модели эмбеддингов с колонкой в схеме api и не стартует при расхождении. Недоступная модель эмбеддингов на старт не влияет: размерность тогда не проверяется, а прогоны с векторной стадией завершаются ошибкой. Сервис подхватывает прогоны, не завершённые до перезапуска

Справочники и демо-данные api заполняют базу потребностями и кандидатами, из которых можно запустить подбор. `fspdb relevance` пересчитывает веса навыков для фактора стека: без него веса не заданы и стек считает все навыки равными

## 3. Первый ключ и векторы

Ключ роли `client` для основного бэкенда выпускает admin:

```sh
curl -X POST localhost:8002/keys \
  -H "Authorization: Bearer $(sed -n 's/^MATCHER_BOOTSTRAP_ADMIN_KEY=//p' .env)" \
  -H 'Content-Type: application/json' \
  -d '{"name": "backend", "role": "client"}'
```

Ключ из ответа показывается один раз. Векторы карточек сервис считает сам при подборе, но первый прогон по большой базе тогда долго ждёт эмбеддер. Заранее их досчитывает команда, которая пропускает карточки с неизменившимся текстом:

```sh
docker compose exec matcher matcher embed
```

То же в фоне делает `POST /embeddings/refresh` с ключом admin. После массового изменения профилей запустите команду или запрос

## 4. Проверка

```sh
curl localhost:8002/health
```

Ответ `{"status":"ok"}` значит, что сервис запущен. Swagger UI открывается по адресу `http://localhost:8002/docs`. Подбор по потребности запускается ключом `client`:

```sh
curl -X POST localhost:8002/needs/<id потребности>/runs -H "Authorization: Bearer <ключ>"
curl localhost:8002/runs/<id прогона> -H "Authorization: Bearer <ключ>"
```

Первый запрос отвечает 202 с `run_id`, второй показывает статус и, когда он станет `done`, выдачу с разложением по факторам. Идентификаторы демонстрационных потребностей задаёт константа `NEED` в [демо-данных api](../../api/app/db/seeds/demo.py). Состав эндпоинтов — [generated/api.md](generated/api.md)

## Автономный запуск

Сервис можно запустить отдельно от платформы, но без api схемы `match` не будет, и `matcher-db-init` завершится ошибкой по истечении ожидания. Поэтому сначала приведите базу api к схеме миграциями: либо запустите сервис `api` платформы, либо выполните из каталога `api/` с `DATABASE_URL` базы:

```sh
uv run alembic upgrade head
```

Суперпользователя сервера Postgres задаёт корневой `.env`, поэтому его копию нужно создать и при автономном запуске: `cp -n ../.env.example ../.env`. После этого `docker compose up -d --build` в каталоге `matcher/` поднимает Postgres, `matcher-db-init` и сервис. Не запускайте автономный стек и платформу одновременно: у них один контейнер базы и одни порты

## Запуск на хосте

Для разработки сервис запускается из исходников, а Postgres — в контейнере:

```sh
cp -n ../.env.example ../.env
docker compose up -d --wait postgres
docker compose run --rm matcher-db-init
uv sync
uv run alembic upgrade head
uv run matcher serve --port 8002
```

Сервис на хосте берёт настройки из переменных окружения и из `.env` в рабочем каталоге. Адрес базы по умолчанию указывает на `localhost` под ролью `matcher`. Сервис рассчитан на один процесс на одну БД: не запускайте его одновременно на хосте и в контейнере с общей базой

## Тесты и линтеры

```sh
uv run pytest -q -m "not integration"
uv run ruff check . && uv run ruff format --check .
```

Первая команда не требует ни базы, ни моделей. Она включает проверку, что копия LLM-слоя совпадает с taskgen, и проверку, что справочники в [generated/](generated) собраны из текущего кода. Справочники пересобирает `uv run python scripts/gen_docs.py`, копию LLM-слоя — `uv run python scripts/sync_llm.py`

### Интеграционные тесты

Интеграционные тесты идут на своей базе api и требуют обе переменные окружения:

- `MATCHER_DATABASE_URL` — адрес базы под ролью `matcher`: через неё идёт сервис, и на ней тесты проверяют права роли
- `MATCHER_TEST_OWNER_URL` — адрес той же базы под владельцем таблиц api: им тесты готовят данные в транзакции, которая откатывается

Адрес по умолчанию намеренно не задан. Без своей базы тесты пошли бы в рабочую базу разработки и упали бы ложно, как тесты taskgen, поэтому тест без переменной падает с сообщением. Базу готовят так, и порядок важен:

1. Создайте пустую базу на сервере Postgres платформы
2. Из `api/` примените миграции и заполните справочники и демо-данные под владельцем: `uv run alembic upgrade head`, затем `uv run fspdb seed`, `uv run fspdb seed-demo` и `uv run fspdb relevance`, все с `DATABASE_URL` этой базы
3. Выдайте роли `matcher` права скриптом [db-init.sql](../../matcher/db-init.sql) через `psql` с переменными `role`, `password`, `db` и `owner`: он должен выполняться после миграций api
4. Из `matcher/` примените собственные миграции под ролью `matcher`: `uv run alembic upgrade head` с `MATCHER_DATABASE_URL`
5. Запустите `uv run pytest -q -m integration`

Для контейнера платформы по имени `fsp-postgres` и базы `matcher_t1`:

```sh
docker exec fsp-postgres createdb -U fsp matcher_t1
docker exec -i fsp-postgres psql -U fsp -d postgres -v ON_ERROR_STOP=1 \
  -v role=matcher -v password=matcher -v db=matcher_t1 -v owner=fsp < db-init.sql
```

Миграции и данные api (шаг 2) выполняются между этими двумя командами. Скрипт идемпотентен и при повторном запуске задаёт права заново. Те же шаги выполняет CI: [matcher-integration.yml](../../.github/workflows/matcher-integration.yml)

## CI

Два workflow, их порядок и причины разделения описаны в заголовках файлов:

- [matcher.yml](../../.github/workflows/matcher.yml) — гейт pull request: линтер, тесты без базы, проверка копии LLM-слоя и актуальности справочников
- [matcher-integration.yml](../../.github/workflows/matcher-integration.yml) — интеграционные тесты на настоящем Postgres: детектор, а не гейт

## Ограничения образа

- Образ uv в `Dockerfile` не закреплён тегом версии и берётся как `latest`, зависимости сервиса ставятся по `uv.lock` ([generated/libraries.md](generated/libraries.md#контейнеры))
- Первый прогон по большой базе считает векторы всех карточек пула, и его длительность определяет скорость эмбеддера: векторы лучше досчитать заранее командой `matcher embed`
