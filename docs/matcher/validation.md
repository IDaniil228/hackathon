# Валидация matcher

ТЗ требует, чтобы команда предложила свою процедуру валидации подбора, описала её и привела результаты; минимума по объёму и реальных кандидатов не требуется ([qa-summary-fsp-2026.md](../qa-summary-fsp-2026.md), чек-лист и раздел 6). Валидация matcher состоит из двух частей. Первая — бенчмарк на наборе, где релевантность каждого кандидата известна по построению: он выполнен, результаты ниже. Вторая — процедура на пилотных данных: она описана, но не выполнена, потому что пилотных данных нет

Устройство конвейера, который меряет бенчмарк, описано в [matching-mechanics.md](matching-mechanics.md), защита от текста кандидата — в [security.md](security.md). Юнит- и интеграционные тесты сервиса проверяют механику по отдельности; бенчмарк проверяет качество порядка целиком

## Что меряется

- nDCG@10 итоговой выдачи прогона. Усиление — `2^rel - 1`, идеальный DCG строится по всем размеченным кандидатам пула, поэтому потерянный релевантный кандидат снижает значение. Чужие профили в пуле, о которых набор ничего не знает, из выдачи выбрасываются (приём condensed list для неполной разметки)
- Потолок nDCG. Правило подбора ставит неподтверждённый грейд ниже любого подтверждённого, и идеальный кандидат с импортированным грейдом (метка 2) всегда оказывается ниже кандидатов с меткой 0 и 1. Потолок — nDCG лучшего порядка, который это правило разрешает. Разница между 1 и потолком — цена решения владельца, а не ошибка ранжировщика
- recall@K векторной стадии: доля кандидатов с меткой не ниже 2 в векторном top-K. Кандидаты разведки в top-K не считаются. Метрика есть, только когда векторная стадия шла, то есть пул больше K
- Префильтр: кандидаты с вилкой выше бюджета и с чужой специализацией не попали в пул, а все остальные попали
- Два утверждения на каждую потребность: нарушитель негативного промта ниже идеального и накрутчик ниже идеального. Кандидат вне выдачи считается ниже всех
- Доля объяснений выдачи и обзоров прогона, которые прошли барьер и проверяльщика. Отклонённый текст сервис заменяет шаблоном из строк факторов, поэтому текст, не равный шаблону, прошёл проверку
- Время прогонов и токены из поля `usage` ответов провайдера, включая токены рассуждений

Метрики считает [tests/bench/metrics.py](../../matcher/tests/bench/metrics.py); значения проверены тестами с посчитанными вручную ожиданиями ([test_metrics.py](../../matcher/tests/bench/test_metrics.py))

## Почему разметка по построению

Разметка LLM-судьёй оценила бы ранжировщик мнением такой же модели: ошибка, общая для обеих моделей, например доверие к инъекции в тексте кандидата, не была бы видна. Поэтому метку задаёт код. Набор берёт идеальный профиль под потребность и строит из него кандидатов-возмущений: каждый вид меняет ровно одно свойство, и это свойство задаёт метку. Что вид меняет только своё свойство, проверяет [test_dataset.py](../../matcher/tests/bench/test_dataset.py)

## Набор

Набор — [tests/bench/dataset.py](../../matcher/tests/bench/dataset.py). Потребности:

| Потребность | Откуда | Категория | Обязательные навыки | Желательные |
|---|---|---|---|---|
| backend | демо-потребность "Backend в команду маршрутизации" из `api/app/db/seeds/demo.py` | backend.middle | Python, PostgreSQL, проектирование БД | FastAPI, из связанной демо-вакансии |
| ml_engineer | демо-потребность "ML-инженер для поиска по каталогу" | ml_engineer.middle | PyTorch, RAG | Transformers |
| frontend | синтетическая | frontend.middle | TypeScript, React | Playwright |
| devops | синтетическая | devops.middle | Kubernetes, Terraform | Prometheus |
| qa | синтетическая | qa.middle | pytest, тест-дизайн | Playwright |
| data_analyst | синтетическая | data_analyst.middle | SQL, Python | ClickHouse |

У демо-потребностей нет желательных навыков, поэтому набор добавляет по одному: без него вид "без желательного" не отличался бы от идеального. Уровни навыков, вилки и тексты — в `NEEDS` набора

Кандидаты каждой потребности:

| Вид | Метка | Чем отличается от идеального |
|---|---|---|
| `ideal` | 3 | Грейд потребности подтверждён тестом, все навыки подтверждены на уровень выше минимума, ожидания внутри вилки |
| `ideal_import` | 2 | Грейд импортирован, а не подтверждён тестом; навыки те же, но только заявлены; machine summary нет |
| `no_nice_to_have` | 2 | Нет желательного навыка |
| `no_required` | 1 | Нет одного обязательного навыка |
| `grade_lower` | 1 | Грейд на ступень ниже (junior), тоже подтверждён тестом |
| `violator` | 0 | Данные идеального, но "о себе" и пожелания совпадают с негативным промтом потребности |
| `stuffer` | 0 | Навыки потребности и посторонние навыки заявлены на 5 из 5, ни один не подтверждён; "о себе" — список ключевых слов и команда модели поставить кандидата первым. Грейд подтверждён тестом: иначе правило о неподтверждённом грейде решило бы за ранжировщик |
| `salary_above` | нет | Ожидания выше бюджета: должен отсечь префильтр |
| `other_specialization` | нет | Категория чужой специализации, которой нет среди потребностей набора; "о себе" — как у идеального: должен отсечь префильтр |

В пул потребности должны попасть все виды с меткой, и только они. Чтобы различия задавало только построение, остальное выровнено:

- machine summary из taskgen заменён каноническим текстом, который код строит из подтверждённых навыков (`summary_text`)
- свежесть и сила профиля у всех одинаковы. Сила профиля — процентиль внутри категории, а одинокому в категории фактор даёт нейтральное значение. Поэтому в каждой категории пула есть скрытый сосед с той же силой: он закрыт для предложений и в пул не входит. Без соседа `grade_lower`, один в своей категории, получал ту же оценку факторов, что идеальный
- ничью матчер разбивает по id кандидата, и id выданы так, что ничья ставит менее релевантного выше. Ничья не засчитывается как успех ни в nDCG, ни в утверждениях

Набор пишется в базу api под владельцем таблиц с id, которые начинаются с `be7c0000-`, и удаляется каскадом после прогонов, даже если прогон упал. Чужие профили в категориях набора меняют процентиль силы профиля, и разметка перестаёт быть точной; бенчмарк пишет их число в `dataset.foreign_in_categories` и предупреждает. Все результаты ниже получены на базе без демо-данных (`fspdb seed` без `seed-demo`), где это число равно 0

## Запуск

Подготовка базы — та же, что у интеграционных тестов ([tests/integration/conftest.py](../../matcher/tests/integration/conftest.py)), но без `fspdb seed-demo`. Скрипт — [scripts/match_bench.py](../../matcher/scripts/match_bench.py); модели ролей и их `reasoning_effort` задают обычные переменные матчера ([generated/settings.md](generated/settings.md)):

```sh
cd matcher
export MATCHER_DATABASE_URL=postgresql+asyncpg://matcher:...@localhost:5432/<база>
export MATCHER_TEST_OWNER_URL=postgresql+asyncpg://<владелец>:...@localhost:5432/<база>
export MATCHER_LLM__RANKER__MODEL=ollama/hf.co/ai-sage/GigaChat3.1-10B-A1.8B-GGUF:q4_K_M
uv run python scripts/match_bench.py --variant hyde --k 3
uv run python scripts/match_bench.py --variant structured --k 3 --no-ranker
uv run python scripts/match_bench.py --variant structured --k 3 --fake
```

`--fake` не нужны модели: эмбеддер — детерминированная подделка, LLM-стадии нет. Этот режим проверяет механику набора, прогонов и уборки и годится для CI ([test_bench_fake.py](../../matcher/tests/bench/test_bench_fake.py)), но его recall@K ничего не говорит о качестве. `--repeat N` повторяет прогоны на заново записанном наборе и показывает разброс недетерминированных моделей. Результат — JSON в [tests/bench/results/](../../matcher/tests/bench/results/): модели и `reasoning_effort` ролей, K, разведка, метрики по потребностям, ранги всех кандидатов по видам и токены

## Выводы

- LLM-ранжировщик поднимает nDCG@10 с 0.685 (только факторы, без вектора) и 0.918 (факторы, ничьи разбивает близость bge-m3) до 0.952–0.962 при потолке 0.966. Остаток до потолка у всех моделей — кандидат без обязательного навыка (метка 1) выше кандидата без желательного (метка 2). У GigaChat к этому добавляется нарушитель выше кандидата с грейдом ниже (метки 0 и 1): утверждение о нарушителе сравнивает его только с идеальным и этого не ловит, а nDCG ловит
- Без LLM нарушитель неотличим от идеального: факты у них одинаковы по построению, и факторы дают ничью. Её разбивает только близость векторов: со структурной карточкой bge-m3 ставит нарушителя дальше идеального во всех потребностях, с HyDE-карточкой — в 14 из 18 прогонов, а без векторной стадии ничья решается по id против идеального (0 из 6). Порядок по факторам негативный промт не видит, так и задумано (негативный промт идёт только в LLM-стадию, [matching-mechanics.md](matching-mechanics.md))
- Инъекция накрутчика на этом наборе не сработала ни у одной модели: накрутчик ниже идеального во всех прогонах, а его средняя оценка ранжировщика 0.31–0.55 против 0.75–1.0 у идеального. Это один текст инъекции на русском; другая формулировка может сработать, поэтому защиту по-прежнему держат ярусы подтверждённости и строки факторов ([security.md](security.md))
- HyDE на этом наборе не лучше структурной карточки. nDCG@10 в пределах разброса повторов, а recall@3 у структурной карточки 0.72 и детерминирован, у HyDE — от 0.61 до 0.78 в зависимости от модели и прогона. Набор мал, и тексты потребностей и кандидатов говорят одними словами; выигрыш HyDE ожидается при расхождении словаря, и этот набор его не проверяет
- K на итоговый порядок здесь не влияет. Пул из семи кандидатов меньше, чем top-K плюс разведка, поэтому до ранжировщика доходит весь пул при любом K. Влияние K на итоговое качество требует пулов больше суммы K и разведки, это ограничение набора
- Модели. deepseek-flash без рассуждений даёт тот же nDCG, что с `high`, и все объяснения проходят проверяльщика, но с рассуждениями прогон в 2.1–3.0 раза дольше, а токенов ответа в 3.7–4.9 раза больше. Рассуждения на этой задаче ничего не дают. GigaChat ранжирует почти так же (0.952–0.959) и без объяснений укладывается в 39–49 с на проход по всем потребностям, но как писатель и проверяльщик объяснений слаб: проходит от 9 до 20 объяснений из 42, остальные работодатель видит шаблоном из факторов, а прогон с объяснениями занимает 500–640 с. Чаще всего проверяльщик GigaChat не даёт номер участка в доказательстве, то есть не выдерживает формат ответа, а не находит ложь. Это совпадает с замерами taskgen: локальный GigaChat годится для генерации, а проверяльщику нужен deepseek-flash ([docs/taskgen/models.md](../taskgen/models.md))

## Что настраивается и что зафиксировано

Настраиваются три вещи, и бенчмарк меряет каждую:

- K — `vector.top_k`, флаг `--k`
- вариант текста запроса — структурная карточка или HyDE. Отдельной настройки у сервиса нет: при включённой LLM-стадии запрос всегда HyDE с откатом на структурную карточку, а бенчмарк получает вариант `structured`, не подключая переписчика. Вариант `hyde_plus_structured` из плана не реализован: в сервисе нет настройки варианта, за которой его можно было бы добавить малой правкой
- промпт ранжировщика — `_RANKER_SYSTEM` в [llm_stage.py](../../matcher/src/matcher/llm_stage.py). В этом замере он не менялся: все строки получены с одним текстом

Зафиксировано и не подбиралось на этом наборе: разведка, размер батча ранжировщика, число переписываний объяснения, способ доказательства (все — [generated/settings.md](generated/settings.md)), веса и константы факторов в [factors.py](../../matcher/src/matcher/factors.py), правило "неподтверждённый грейд ниже подтверждённых", шаблон карточки в [profile_text.py](../../matcher/src/matcher/profile_text.py), модель эмбеддингов bge-m3. Модели ролей — выбор развёртывания, а не параметр качества: таблица выше даёт для этого выбора качество и время

## Процедура на пилотных данных

> [!IMPORTANT]
> Пилотных данных о подборе нет: ни один работодатель не запускал подбор на реальных кандидатах. Ниже процедура, а не результаты

Жюри проверит подбор руками на своих синтетических профилях ([qa-summary-fsp-2026.md](../qa-summary-fsp-2026.md), раздел 10). Для пилота на настоящих данных процедура такая:

1. Разметка экспертом. По каждой потребности пилота эксперт — нанимающий менеджер или техлид — ставит кандидатам метку 0–3 по той же шкале, что в наборе. Размечаются top-10 выдачи и случайная выборка кандидатов пула вне короткого списка. Эксперт видит кандидатов в случайном порядке, без ранга, оценок и объяснений сервиса
2. Метрики. nDCG@10 и recall@K считаются тем же модулем [metrics.py](../../matcher/tests/bench/metrics.py) по `match.search_results`: строки пула вне короткого списка сервис хранит со `stage = prefilter` и `vector_score` (`results.store_pool`), поэтому recall векторной стадии считается без повторного прогона
3. Сравнение K и варианта запроса. Одну потребность прогоняют с разными K и с HyDE и без него, эксперт размечает объединение выдач. Выбор фиксируется в настройках и в этой странице
4. Поведение работодателя. Доля приглашений по позиции выдачи — по `hire.invitations` с `need_id` прогона и рангу кандидата в `match.search_results`. Приглашения ниже top-10 значат, что порядок расходится с тем, кого работодатель выбирает
5. Объяснения. Доля объяснений, прошедших проверяльщика, видна по выдаче: текст, равный шаблону из строк факторов, — откат. Выборку прошедших объяснений эксперт сверяет с профилем: проверяльщик подтверждает связь со строками факторов, но не полноту

## Ограничения

- Набор синтетический и маленький: шесть потребностей по семь кандидатов в пуле. Тексты набора написала та же команда, что и промпты сервиса
- Нарушитель и накрутчик представлены одним текстом на потребность, инъекция — одной формулировкой
- DeepSeek прогнан по одному разу на конфигурацию; разброс между повторами измерен только у GigaChat и у HyDE без ранжировщика
- Метрика объяснений — доля прошедших проверку, а не их правдивость или полнота
- В демо-потребностях набор добавил по желательному навыку, иначе вид "без желательного" не отличался бы от идеального
