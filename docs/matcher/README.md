# Документация сервиса matcher

matcher — сервис платформы, который по потребности работодателя подбирает кандидатов, ранжирует их и объясняет, почему каждый стоит на своём месте. Код сервиса лежит в [`matcher/`](../../matcher), условие задачи и перечень документации — в [разборе ТЗ](../qa-summary-fsp-2026.md#7-сдача-репозиторий-документация)

Разделы идут в порядке обязательного перечня документации из ТЗ. Раздела про механику тестирования здесь нет: это забота сервиса [taskgen](../taskgen/README.md)

1. [Архитектура](architecture.md) — место сервиса в платформе, доступ к данным api, компоненты, жизненный цикл прогона и копия LLM-слоя taskgen
2. [Механика подбора и логика категоризации](matching-mechanics.md) — стадии конвейера, факторы, порядок выдачи, проверенные объяснения, уточнение, фильтры и работа без части служб
3. [Валидация](validation.md) — что и как проверяется, набор для проверки и результаты
4. [Недоверенный текст и данные](security.md) — куда текст кандидата и работодателя попадает в модели, какие данные видит сервис, что защищает и что остаётся открытым
5. [API](generated/api.md) — эндпоинты, роли, тела запросов, ответы и коды ошибок; спецификация — [openapi.json](generated/openapi.json)
6. [Настройки](generated/settings.md) — все настройки сервиса с переменными окружения и значениями по умолчанию
7. [Библиотеки и компоненты](generated/libraries.md) — версии зависимостей и образы контейнеров
8. [Развёртывание](deployment.md) — сборка, запуск в Docker и на хосте, первый ключ, векторы, тесты и CI

Схем интеграции с FSP ID у matcher нет: он не аутентифицирует пользователей и не ходит во внешние службы платформы, кроме taskgen и провайдеров LLM. Результаты ФСП он читает из профиля кандидата в базе api

Файлы в [`generated/`](generated) собирает из кода `uv run python scripts/gen_docs.py` в каталоге `matcher/`; тест `tests/test_docs_generated.py` падает, если они отстали от кода
