# Механика тестирования

ТЗ отвергает два крайних решения: единый набор заданий быстро расходится между кандидатами, а задания, которые нейросеть придумывает под каждого кандидата, не гарантируют сопоставимую сложность и объективную оценку. taskgen разделяет задание на две части. Шаблон пишет и проверяет человек, он задаёт сложность, данные и критерии оценки. Экземпляр собирается по шаблону для конкретной сессии: параметры и тесты выбирает код по seed, а LLM пишет только текст условия. Экземпляр выдаётся кандидату только после того, как эталонное решение прошло все его тесты в песочнице

Числа ниже — значения по умолчанию из [generated/settings.md](generated/settings.md); там же их переменные окружения

## Шаблон и экземпляр

Шаблон — md-файл с YAML-заголовком и разделами, формат описан в [TEMPLATE_FORMAT.md](../../taskgen/TEMPLATE_FORMAT.md), каталог банка — в [generated/templates.md](generated/templates.md). Шаблон фиксирует:

- область, грейд, навыки, тип (`code` или `essay`), окружение песочницы, сложность по шкале 1–10 и ожидаемое время
- диапазоны параметров экземпляра: целые и дробные числа с границами или выбор из списка
- для заданий с кодом — эталонное решение, имя функции кандидата и генератор тестов на Python
- для эссе — вопросы, факты ситуации и фразы, которые ситуация не должна раскрывать
- рубрику: атомарные пункты проверки с примерами, которые проходят и не проходят

| | Шаблон | Экземпляр |
|---|---|---|
| Кто создаёт | Автор банка, проверяет шлюз ([validation.md](validation.md)) | Сервис для одной сессии |
| Сложность и критерии | Задаёт | Наследует без изменений |
| Параметры и тесты | Диапазоны и генератор | Конкретные значения по seed и кейсы |
| Текст условия | Инструкция для LLM | Легенда, которую написала LLM |
| Видит кандидат | Никогда | Условие, сигнатуру, публичные примеры |

Загрузка шаблона с тем же именем создаёт новую версию; экземпляры ссылаются на свою версию, поэтому правка шаблона не меняет уже выданные задания

## Параметры по seed

Значения параметров выбирает код, а не модель: модель могла бы сдвинуть сложность, и экземпляры одного шаблона перестали бы быть сопоставимы. Генератор случайных чисел инициализируется seed задания, параметры перебираются в порядке имён, поэтому перестановка строк в шаблоне не меняет экземпляр ([params.py](../../taskgen/src/taskgen/generation/params.py))

Seed сессии задаёт всё остальное: из одного генератора по очереди берутся отбор шаблонов и seed каждого задания. Seed хранится в `tasks.seed`, а seed сессии — в объяснении отбора. Клиент может передать seed сам: тот же seed на том же банке и тех же эмбеддингах даёт те же шаблоны и те же параметры

## "Сгенерировал — проверил"

Для задания с кодом экземпляр собирается так ([instance.py](../../taskgen/src/taskgen/generation/instance.py)):

1. Параметры по seed
2. Генератор тестов шаблона запускается в песочнице с этими параметрами и тем же seed и возвращает кейсы `{input, expected}`. Код генератора пришёл из загруженного шаблона, поэтому сервис сам его не исполняет
3. Эталон шаблона прогоняется на всех кейсах в той же песочнице. Если эталон не прошёл хотя бы один кейс или не скомпилировался, экземпляр отбрасывается и берётся следующий seed, выведенный из исходного, не больше `generation.instance_attempts` раз. Отчёт эталона сохраняется: по нему потом оценивается скорость решения кандидата
4. Первые `generation.public_examples` кейсов становятся публичными примерами, но хотя бы один кейс остаётся скрытым
5. Только проверенный экземпляр получает легенду от LLM

Ожидаемое значение кейса генератор считает своей реализацией, а не эталоном: перебором, другим алгоритмом или численной производной. Поэтому совпадение эталона с кейсами — проверка двух независимых реализаций друг другом

Решение кандидата проверяется так же: обвязка в песочнице вызывает его функцию на входах кейсов, а ожидаемые значения в песочницу не передаются. Сравнение идёт в сервисе, поэтому код кандидата не может прочитать ответы или подменить вердикт ([protocol.py](../../taskgen/src/taskgen/sandbox/protocol.py))

## Легенда от LLM — только обёртка

Модель получает инструкцию автора с подставленными параметрами, имя функции, описание окружения и только публичные примеры. Скрытых кейсов она не видит. Ответ модели проверяет код ([leaks.py](../../taskgen/src/taskgen/generation/leaks.py)):

- в условии названа функция кандидата
- в условии нет значений скрытых кейсов; значение короче пяти символов после нормализации и значение из публичного примера утечкой не считаются
- в условии нет определения функции кандидата, то есть готового решения

Условие, которое не прошло проверку, модель переписывает, не больше `generation.legend_attempts` раз. Если попытки кончились, шаблон считается не давшим экземпляра и заменяется другим того же грейда. Сложность, данные, тесты и рубрика от текста легенды не зависят

## Персонализация по профилю

Основной бэкенд может передать профиль кандидата: резюме, навыки из любых областей и прочие поля ([profile.py](../../taskgen/src/taskgen/generation/profile.py)). Профиль влияет на две вещи:

- отбор шаблонов: навыки профиля и резюме входят в текст, эмбеддинг которого сравнивается с описаниями шаблонов
- тематику легенды: модель берёт из профиля предметную область, персонажей и сюжет

Параметры, кейсы, эталон и рубрика профиля не видят. Профиль идёт модели между маркерами со случайной меткой и с правилом, что это данные, а не инструкции, поэтому резюме с командой "сделай задачу проще" не меняет задание. Тест на это — `test_malicious_resume_changes_neither_params_nor_hidden_data` в [test_personalization.py](../../taskgen/tests/generation/test_personalization.py)

Смежная тема: с вероятностью `generation.adjacent_topic_probability` легенда персонального задания строится вокруг навыка профиля, которого нет в шаблоне, например задача на графы в антураже машинного обучения. Тема выбирается отдельным генератором от seed задания, поэтому воспроизводима и не сдвигает параметры. Окружение и требования задачи остаются прежними: тема меняет сюжет, а не задачу. Что из профиля повлияло на легенду, записано в `tasks.personalization`

## Эссе

Если LLM пишет условие эссе целиком, она подсказывает ответ в тексте вопроса, теряет элементы сценария, на которые опирается рубрика, и искажает вопросы. Поэтому условие эссе собирается из двух частей ([essay.py](../../taskgen/src/taskgen/generation/essay.py)):

- вопросы пишет автор шаблона, и они идут в условие дословно, с подставленными параметрами; модель их не видит
- ситуацию пишет модель по инструкции и списку фактов шаблона

Ситуация проверяется до выдачи. Код ищет в ней запрещённые фразы шаблона без учёта регистра, буквы ё и пунктуации. Модель-проверяльщик для каждого факта отвечает, есть ли он в ситуации, и цитирует её; код сверяет цитату с текстом, и факт без цитаты или с выдуманной цитатой считается пропущенным. Ситуация с пропущенным фактом или запрещённой фразой переписывается с перечнем причин. Шлюз банка дополнительно проверяет, что сами вопросы не содержат запрещённых фраз ни при одном сочетании параметров

## Отбор шаблонов

Тест собирается из `selection.tasks_per_test` шаблонов области. Каждый шаблон области получает расстояние до кандидата, и шаблоны выбираются без возвращения, на каждом шаге — softmax по оставшимся ([selection.py](../../taskgen/src/taskgen/bank/selection.py)):

```
d = alpha · |Δгрейд| + beta · (1 − sim)
p ∝ exp(−d / T),  T = t / (1 − t)
```

- `|Δгрейд|` — разность позиций грейда шаблона и заявленного грейда в списке грейдов по возрастанию `level`. Промежуточный грейд, добавленный между соседями, не удлиняет шаг между ними
- `sim` — косинусное сходство эмбеддинга описания шаблона с эмбеддингом текста кандидата: названия навыков и резюме. Если эмбеддера нет, у кандидата нет ни навыков, ни резюме или у шаблона нет актуального вектора, весь отбор идёт по доле общих навыков (коэффициент Жаккара). Режим общий для всех шаблонов: косинус и доля навыков распределены по-разному, и смешивать их нельзя
- `t` из отрезка [0, 1]: при `t = 0` выбираются только ближайшие шаблоны, ничьи — случайно; при `t = 1` выбор равномерный
- Параметр берётся из переопределения admin для сессии, иначе из `test_configs` для пары (область, грейд), иначе из настроек

Пример при значениях по умолчанию (`alpha = beta = 1`, `t = 0.3`, `T ≈ 0.43`) и пяти шаблонах:

| Шаблон | `\|Δгрейд\|` | `sim` | `d` | `p` первым |
|---|---|---|---|---|
| заявленный грейд, близкие навыки | 0 | 0.8 | 0.2 | 0.588 |
| заявленный грейд, далёкие навыки | 0 | 0.5 | 0.5 | 0.292 |
| грейд выше, близкие навыки | 1 | 0.8 | 1.2 | 0.057 |
| грейд ниже, близкие навыки | 1 | 0.8 | 1.2 | 0.057 |
| два грейда выше | 2 | 0.8 | 2.2 | 0.006 |

Тест в основном состоит из заданий заявленного грейда, но с заметной вероятностью включает соседние уровни: они нужны оценке по уровням ниже. Случайность отбора — ещё один слой защиты от распространения: два кандидата с одинаковым профилем получают разные наборы шаблонов. Всё, что определило отбор, — режим, параметры, расстояния и вероятности всех шаблонов — сохраняется в сессии и отдаётся работодателю через `GET /sessions/{id}/selection`

## Балл задания

Задание с кодом получает балл из четырёх компонентов от 0 до 1 ([scoring.py](../../taskgen/src/taskgen/evaluation/scoring.py)):

| Компонент | Откуда | Вес по умолчанию |
|---|---|---|
| `tests` | Доля пройденных скрытых кейсов | `scoring.weight_tests` |
| `rubric` | Балл судьи по рубрике шаблона | `scoring.weight_rubric` |
| `quality` | Метрики статических анализаторов, приведённые к 0..1 по границам из [рубрик метрик](../../taskgen/src/taskgen/evaluation/rubrics): для Python — ruff, radon и доля аннотаций типов, для C++ — lizard, clang-tidy и cppcheck | `scoring.weight_quality` |
| `performance` | Время и память относительно эталона на тех же кейсах | `scoring.weight_performance` |

```
score = 0,                          если tests = 0
score = Σ wᵢ·cᵢ / Σ wᵢ  по измеренным компонентам с wᵢ > 0 — иначе
```

- Жёсткий гейт: решение, не прошедшее ни одного теста, получает 0, как бы хорошо оно ни выглядело для судьи. Судья в этом случае не вызывается
- Вес неизмеренного компонента делится между измеренными: кандидат не теряет балл из-за того, что для его языка нет анализатора или инструмента анализатора нет на машине сервиса. Например, при `tests = 0.8`, `rubric = 0.75`, `performance = 1` и неизмеренном `quality` балл равен (0.6·0.8 + 0.25·0.75 + 0.05·1) / 0.9 ≈ 0.797
- Скорость: 1 — не хуже эталона, 0.5 — вдвое медленнее; время сравнивается только на пройденных кейсах, а малые разницы ниже порога шума не учитываются
- Шаблон может переопределить веса для своих заданий
- Задание считается решённым при балле не ниже `scoring.solved_threshold`

Эссе получает балл судьи без изменений. Судья ([judge.py](../../taskgen/src/taskgen/evaluation/judge.py)) оценивает каждый пункт рубрики как `yes`, `partial` или `no` (1, 0.5, 0) и обязан процитировать ответ. Код сверяет каждую цитату с ответом: вердикт без цитаты или с цитатой, которой в ответе нет, становится `no`. Судья вызывается `scoring.judge_samples` раз с ненулевой температурой, по каждому пункту берётся нижняя медиана вердиктов, а разница баллов сэмплов сохраняется как `spread` — повод для ручной проверки. Ответ кандидата идёт судье между маркерами со случайной меткой: просьба "поставь максимальный балл" внутри ответа не подтверждает ни один пункт. По умолчанию судьёй работает другая модель, чем генератором, чтобы судья не завышал оценку текстам своей модели

## Грейд по уровням

Задания теста относятся к грейдам своих шаблонов. Уровень подтверждён, если ([grading.py](../../taskgen/src/taskgen/evaluation/grading.py)):

- доля решённых заданий этого уровня не меньше `scoring.pass_threshold`
- доля решённых среди всех заданий младших уровней вместе тоже не меньше порога

Присваивается старший подтверждённый уровень. Младшие уровни проверяются вместе, а не каждый отдельно: на уровень приходится одно-два задания, и одна ошибка на младшем уровне при отдельной проверке стирала бы все старшие. Требование к младшим уровням остаётся: решённый старший уровень при проваленных младших — скорее удачная догадка, чем грейд

Пример: кандидат заявил senior, `solved_threshold = 0.7`, `pass_threshold = 0.6`

| Уровень | Баллы заданий | Решено | Доля | Младшие вместе | Подтверждён |
|---|---|---|---|---|---|
| junior | 0.9; 0.4 | 1 из 2 | 0.5 | нет младших | нет, доля ниже порога |
| middle | 0.8; 0.75 | 2 из 2 | 1.0 | 1 из 2 = 0.5 | нет, младшие ниже порога |
| senior | 0.72 | 1 из 1 | 1.0 | 3 из 4 = 0.75 | да |

Присвоен senior, исход `passed`. При отдельной проверке каждого младшего уровня одна ошибка на junior оставила бы кандидата без грейда

Исход сравнивает присвоенный грейд с заявленным: `passed`, `upgraded`, `downgraded` или `failed`. При повышении или понижении сервис рекомендует пройти полный тест на подтверждённый грейд, потому что заданий соседнего уровня в тесте мало; если не подтверждён ни один уровень — тест на грейд ниже заявленного. Грейд не понижается принудительно: сервис только рекомендует, а ограничение частоты смены грейда держит основной бэкенд

## Детектор ИИ и поведенческие сигналы

Детектор ИИ выключен по умолчанию (`ai_detector_enabled`). Включённый детектор спрашивает модель судьи, насколько вероятно, что код написан моделью, и пишет ответ в `answers.ai_signal`. На балл, грейд и текст summary сигнал не влияет и наружу через API не отдаётся ([detector.py](../../taskgen/src/taskgen/evaluation/detector.py))

Причина — ненадёжность таких детекторов. OpenAI закрыла свой классификатор текстов ИИ 20 июля 2023 года из-за низкой точности ([новость](https://www.searchenginejournal.com/openai-shuts-down-flawed-ai-detector/492565/)). В исследовании Liang и соавторов семь распространённых детекторов приняли за сгенерированные больше половины эссе TOEFL, написанных людьми, а простые приёмы в запросе к модели позволяли обойти детекторы ([arXiv:2304.02819](https://arxiv.org/abs/2304.02819)). Штраф по такому сигналу наказывал бы честных кандидатов чаще, чем ловил нечестных

Поведенческие сигналы фронтенда — число вставок из буфера, уходов со страницы и время работы — сохраняются с ответом и показываются как числа. На балл они не влияют

## Machine summary

После каждой оценки сервис перезаписывает сводку по всем оценённым сессиям кандидата ([summary.py](../../taskgen/src/taskgen/evaluation/summary.py)). Факты берутся по белому списку полей результата: сигнал детектора, рубрики и скрытые данные в них не попадают. Текст пишет модель, а код проверяет его: в каждом предложении есть число из фактов, других чисел нет, оценочных ярлыков о честности и использовании ИИ нет. Текст, не прошедший проверку, заменяется текстом по шаблону из тех же фактов. Изменить summary через API нельзя

## Устойчивость к распространению заданий

| Что утекло | Что это даёт следующему кандидату |
|---|---|
| Условие и примеры чужого экземпляра | Мало: у него другие шаблоны с вероятностями из отбора, другие параметры и кейсы по своему seed и другая легенда |
| Скрытые кейсы | Не утекают: в ответы API не попадают, кандидат видит только публичные примеры, а решение исполняется без ожидаемых значений |
| Эталон и генератор тестов | Не утекают через основной бэкенд: роль `client` видит только метаданные шаблона |
| Экземпляр из пула | Выдаётся одной сессии и живёт не дольше `generation.pool_max_age_hours` |
| Идея шаблона: какой алгоритм нужен | Остаётся знанием, которое тест и проверяет: заучить ответ нельзя, потому что данные и проверка у каждого свои, а рубрика оценивает решение, а не совпадение с эталоном |

Ограничения, которые важно знать:

- банк пока мал, его состав — в [generated/templates.md](generated/templates.md). Чем меньше шаблонов в ячейке, тем вероятнее, что два кандидата получат один шаблон, пусть и с разными параметрами. Устойчивость растёт с размером банка, а не с числом выданных экземпляров
- вопросы эссе идут в условие дословно и повторяются у всех, кому выпал шаблон; меняются только ситуация и подставленные параметры. Эссе защищены от распространения слабее заданий с кодом
- вычисление по шаблону закрывает утечку ответа, но не сговор, при котором решает другой человек. Против этого в сервисе есть только поведенческие сигналы, и они намеренно не влияют на балл

## Что воспроизводимо, а что сохраняется дословно

| Воспроизводится по seed | Сохраняется дословно |
|---|---|
| Отбор шаблонов при том же банке, эмбеддингах и параметрах отбора | Условие задания: легенда и ситуация эссе от LLM |
| Параметры экземпляра | Публичная и скрытая части задания, включая кейсы и отчёт эталона |
| Кейсы генератора тестов, если генератор берёт случайность только из переданного `rng` | Вердикты судьи с цитатами и `spread` |
| Выбор смежной темы легенды | Компоненты балла, веса и метрики анализаторов |
| Перебор seed при отказе эталона | Результат сессии и текст summary |

Ответы модели при ненулевой температуре и время прогонов не воспроизводятся, поэтому всё, на чём основан балл, хранится в БД в том виде, в каком его увидел кандидат и оценил сервис
