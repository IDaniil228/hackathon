# Валидация taskgen

ТЗ не даёт эталонной разметки кандидатов, поэтому валидация сервиса состоит из двух частей. Первая проверяет механику, которой не нужны данные о кандидатах: банк шаблонов, генерацию, песочницу, судью и формулы. Она выполнена, её результаты ниже. Вторая — статистическая процедура на ответах пилотных кандидатов: она описана и подготовлена, но не выполнена, потому что пилотных данных нет

Устройство механики, которую проверяют тесты, описано в [testing-mechanics.md](testing-mechanics.md)

## Шлюз банка шаблонов

Шлюз — [tests/seed/test_seed_templates.py](../../taskgen/tests/seed/test_seed_templates.py). Он проверяет банк из `taskgen/seed` теми же функциями, которыми сервис генерирует экземпляр, и в реальной песочнице Piston:

| Проверка | Что ловит |
|---|---|
| Шаблон разбирается и лежит в каталоге своей области и грейда | Ошибки формата и шаблон не в своей ячейке |
| Сложность шаблонов одной ячейки (область, грейд) различается не больше чем на `MAX_CELL_SPREAD` | Несопоставимые по сложности задания одного уровня |
| Банк собирает тест состава из настроек на любую ячейку: в каждой ячейке шаблонов каждого типа не меньше квоты `min_claimed_per_kind`, в области — не меньше заданий этого типа в тесте; набор импортируется в БД со справочниками | Тест, который не соберётся или выйдет короче, и навыки вне справочника или чужой области. Текст ошибки называет область, грейд, тип и число шаблонов |
| В каждой ячейке не меньше `MIN_QUIZ_PER_CELL` задачек | Одна задачка ячейки, которая выпадала бы каждому кандидату |
| У задачки не меньше двух вариантов кейса, у каждого ровно один верный ответ и не меньше трёх неверных, а верные ответы различаются хотя бы у двух вариантов | Задачку, утёкший ответ которой подходит к любому экземпляру, и неоднозначный ключ |
| У всех вариантов задачки один набор ответов, и каждый верный ответ закрыт хотя бы одной фразой «Нельзя раскрывать» | Вариант, который узнаётся по набору ответов, и кейс, который может назвать ответ прямо |
| Вопрос и факты задачки не содержат запрещённых фраз ни при одном сочетании параметров | Вопрос, который раскрывает ответ, и факт, с которым кейс никогда не пройдёт проверку |
| Вакансии называют только коды справочников | Вакансию, которую нельзя подать в отбор |
| На seed 0, 1 и 2 генератор тестов даёт не меньше `MIN_CASES` кейсов, не все с одним ответом, а входы помещаются в запрос к Piston | Вырожденные и слишком большие наборы тестов |
| Эталон проходит все кейсы на каждом seed | Расхождение эталона и генератора. Генератор считает ожидаемые значения своей реализацией — перебором, другим алгоритмом или численной производной, — поэтому совпадение подтверждает обе реализации |
| Каждое неверное решение проваливает хотя бы один кейс на каждом seed | Слабые тесты. Неверные решения — мутанты эталона из [mutants.py](../../taskgen/tests/seed/mutants.py), каждый воспроизводит правдоподобную ошибку кандидата, и решения, которые возвращают константу и не смотрят на вход |
| У каждого шаблона с кодом есть мутанты | Шаблон, тесты которого никто не пытался обмануть |
| Вопросы эссе не содержат запрещённых фраз ни при одном сочетании параметров | Вопрос, который сам раскрывает ответ |

Шлюз входит в набор тестов и запускается так, нужны Postgres и Piston с пакетами окружений ([deployment.md](deployment.md)):

```sh
cd taskgen
uv run pytest -q tests/seed
```

Числа шлюза считает [scripts/gate_stats.py](../../taskgen/scripts/gate_stats.py) теми же функциями: шлюз только утверждает, а скрипт считает кейсы, прогоны эталона и пойманные решения. Ему нужен только Piston:

```sh
cd taskgen
uv run python scripts/gate_stats.py
```

> [!WARNING]
> При полной загрузке процессора машины, когда параллельно шли другие наборы тестов, часть прогонов неверных решений на C++ упала с "превышено время компиляции": Piston ограничивает компиляцию своим лимитом, а не лимитом запуска сервиса. На свободной машине тот же шлюз проходит. В рабочем развёртывании Piston не стоит делить с тяжёлыми задачами

## Процедура на пилотных данных

> [!IMPORTANT]
> Пилотных данных о кандидатах нет: ни одна сессия не прошла реальный кандидат. Ниже — процедура и готовый к запуску запрос, а не результаты. Чисел о дискриминативности, согласованности грейда и разбросе судьи в этой документации нет, потому что их не из чего посчитать

Данные для процедуры сервис уже сохраняет: результат каждой сессии с баллами и решённостью заданий, шаблон каждого задания, вердикты и `spread` судьи в `answers.judge`. Процедура:

1. Пилот. Каждый участник проходит тест два раза на разных экземплярах: второй раз с другим seed и, если банк позволяет, на других шаблонах той же ячейки. Для части участников нужен независимый эксперт, который ставит грейд по собеседованию, без доступа к результатам теста
2. Трудность шаблона, p — доля решивших задания шаблона. Шаблон с p около 0 или около 1 не разделяет кандидатов и уходит на доработку
3. Дискриминативность шаблона, индекс D — разность долей решивших задания шаблона среди верхних и нижних 27 % кандидатов по среднему баллу сессии, внутри пары (область, заявленный грейд). Это классический индекс дискриминации теории тестов. Шаблон с низким или отрицательным D сильные решают не чаще слабых, его нужно пересмотреть
4. Согласованность грейда — доля пар прохождений одного участника, давших один и тот же грейд, и каппа Коэна по парам. Разные экземпляры одного шаблона должны давать один грейд; расхождение указывает на шаблон, чья сложность зависит от параметров
5. Соответствие экспертной оценке — доля совпадений грейда теста с грейдом эксперта и матрица ошибок: тест чаще завышает или занижает
6. Разброс судьи — распределение `spread` по пунктам рубрики и повторная оценка одних и тех же ответов. Пункт рубрики с большим разбросом переписывается атомарнее

Трудность и дискриминативность по всем оценённым сессиям считает [scripts/item_analysis.sql](../../taskgen/scripts/item_analysis.sql). Запрос проверен на схеме и на синтетических строках в откатываемой транзакции:

```sh
cd taskgen
docker compose exec -T db psql -U taskgen -d taskgen < scripts/item_analysis.sql
```

## Ограничения

- Нет пилотных данных и экспертной разметки, поэтому критерии ТЗ о согласованности грейда, дискриминативности и соответствии экспертной оценке пока подкреплены только процедурой, а не числами
- Шлюз проверяет шаблоны с кодом на трёх seed; другие seed дают другие значения параметров, и шлюз их не видит. Сервис компенсирует это проверкой каждого экземпляра эталоном перед выдачей
- Эссе проверяются только по формату и по запрещённым фразам в вопросах. Качество ситуаций от модели проверяется при каждой генерации, но статистики их отказов нет
- Что факты варианта задачки подходят к любому значению параметров шаблона, например к любому домену, проверил автор банка, а не код: смысл факта код не читает ([TEMPLATE_FORMAT.md](../../taskgen/TEMPLATE_FORMAT.md))
- Что факты варианта задачки исключают каждый неверный ответ, проверил автор банка, а не код. Слепой решатель ловит неоднозначный кейс, но выключен по умолчанию; статистики его ложных отказов на настоящих моделях нет, хотя итог решателя сохраняется в каждом задании
- Сопоставимость сложности внутри ячейки задана оценкой автора шаблона `difficulty` и проверяется как разброс этой оценки; эмпирическая проверка — трудность p из процедуры выше
