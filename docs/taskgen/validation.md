# Валидация taskgen

ТЗ не даёт эталонной разметки кандидатов, поэтому валидация сервиса состоит из двух частей. Первая проверяет механику, которой не нужны данные о кандидатах: банк шаблонов, генерацию, песочницу, судью и формулы. Она выполнена, её результаты ниже. Вторая — статистическая процедура на ответах пилотных кандидатов: она описана и подготовлена, но не выполнена, потому что пилотных данных нет

Устройство механики, которую проверяют тесты, описано в [testing-mechanics.md](testing-mechanics.md)

## Шлюз банка шаблонов

Шлюз — [tests/seed/test_seed_templates.py](../../taskgen/tests/seed/test_seed_templates.py). Он импортирует банк из `taskgen/seed` тем же кодом, что `taskgen import` и API загрузки, в реальной песочнице Piston, и сверх импорта проверяет правила банка целиком. Проверки шаблона с кодом живут в сервисе, в [bank/validation.py](../../taskgen/src/taskgen/bank/validation.py): их выполняет каждый импорт, а не только шлюз, и шаблон, который их не прошёл, в банк не попадает:

| Проверка | Что ловит |
|---|---|
| Шаблон разбирается и лежит в каталоге своей области и грейда | Ошибки формата и шаблон не в своей ячейке |
| Сложность шаблонов одной ячейки (область, грейд) различается не больше чем на `MAX_CELL_SPREAD` | Несопоставимые по сложности задания одного уровня |
| Банк собирает тест состава из настроек на любую ячейку: в каждой ячейке шаблонов каждого типа не меньше квоты `min_claimed_per_kind`, в области — не меньше заданий этого типа в тесте; набор импортируется в БД со справочниками | Тест, который не соберётся или выйдет короче, и навыки вне справочника или чужой области. Текст ошибки называет область, грейд, тип и число шаблонов |
| В каждой ячейке не меньше `MIN_QUIZ_PER_CELL` задачек | Одна задачка ячейки, которая выпадала бы каждому кандидату |
| У задачки не меньше двух вариантов кейса, у каждого ровно один верный ответ и не меньше трёх неверных, а верные ответы различаются хотя бы у двух вариантов | Задачку, утёкший ответ которой подходит к любому экземпляру, и неоднозначный ключ |
| У всех вариантов задачки один набор ответов, и каждый верный ответ закрыт хотя бы одной фразой «Нельзя раскрывать» | Вариант, который узнаётся по набору ответов, и кейс, который может назвать ответ прямо |
| Вопрос и факты задачки не содержат запрещённых фраз ни при одном сочетании параметров | Вопрос, который раскрывает ответ, и факт, с которым кейс никогда не пройдёт проверку |
| Вакансии называют только коды справочников | Вакансию, которую нельзя подать в отбор |
| Импорт: на каждом seed от 0 до `import_check.seeds − 1` генератор тестов даёт не меньше `MIN_CASES` кейсов, не все с одним ответом, а входы помещаются в запрос к Piston | Вырожденные и слишком большие наборы тестов |
| Импорт: каждое верное решение `### id +` проходит все кейсы на каждом seed | Расхождение решения и генератора. Генератор считает ожидаемые значения своей реализацией — перебором, другим алгоритмом или численной производной, — поэтому совпадение подтверждает обе реализации. Второе верное решение, например честное медленное, проверяет ещё и лимиты |
| Импорт: каждое неверное решение `### id -` компилируется и не решено на каждом seed даже при идеальных рубрике, качестве и скорости; то же для решений, которые возвращают константу и не смотрят на вход | Слабые тесты. Неверное решение воспроизводит правдоподобную ошибку кандидата и лежит в самом шаблоне, в разделе «Решения» |
| Разбор: у шаблона с кодом есть хотя бы одно верное и одно неверное решение; импорт: есть обязательная группа кейсов | Шаблон, тесты которого никто не пытался обмануть, и балл решённого у решения с одной ошибкой |
| Вопросы эссе не содержат запрещённых фраз ни при одном сочетании параметров | Вопрос, который сам раскрывает ответ |

Шлюз входит в набор тестов и запускается так, нужны Postgres и Piston с пакетами окружений ([deployment.md](deployment.md)):

```sh
cd taskgen
uv run pytest -q tests/seed
```

Числа шлюза считает [scripts/gate_stats.py](../../taskgen/scripts/gate_stats.py) той же проверкой импорта: шлюз только утверждает, а скрипт считает кейсы, прогоны верных решений и пойманные неверные. Ему нужен только Piston:

```sh
cd taskgen
uv run python scripts/gate_stats.py
```

Что эти числа доказывают и чего не доказывают. Неверные решения написаны теми же авторами, что и тесты, поэтому 100 % — нижняя граница слабости тестов, которую удалось найти, а не доказательство их полноты. Решения-константы ловят тесты, которые не смотрят на ответ, но не тонкие ошибки

> [!WARNING]
> При полной загрузке процессора машины, когда параллельно шли другие наборы тестов, часть прогонов неверных решений на C++ упала с "превышено время компиляции": Piston ограничивает компиляцию своим лимитом, а не лимитом запуска сервиса. На свободной машине тот же шлюз проходит. С проверкой при импорте такой обрыв отклоняет загрузку исправного шаблона с C++, поэтому в рабочем развёртывании Piston не стоит делить с тяжёлыми задачами

## Ложные срабатывания оценки

Набор [tests/evaluation/adversarial](../../taskgen/tests/evaluation/adversarial) проверяет оценку в обе стороны: честный ответ не должен терять балл, а пустой, неверный, не по теме или с инъекцией — получать лишний. Набор состоит из ответов на шаблоны банка — три задания с кодом и три эссе разных областей и грейдов, — у каждого ответа ожидаемый диапазон балла, заданный до прогона. Классы ответов и формат файла описаны в [dataset.py](../../taskgen/tests/evaluation/adversarial/dataset.py). Слабые честные ответы на эссе написала Saiga YandexGPT 8B, они сохранены без правок

Что проверяет код, а не модель, — гейт по тестам, сверку цитат и маркеры — проверяет [test_adversarial.py](../../taskgen/tests/evaluation/adversarial/test_adversarial.py) с судьёй-подделкой, который верит каждому ответу. Прогон на настоящих моделях:

```sh
cd taskgen
uv run python scripts/adversarial_eval.py --out results.json --instances instances.json
```

Экземпляр каждого шаблона собирает генерация сервиса, ответ с кодом проходит песочницу и анализаторы, балл считает `evaluate_task` с судьёй из настроек. Флаги `--judge-*` подключают другого судью, например облачного

### Результаты

Прогон 7 октября 2026 года, ветка `tg-evalcheck`, `judge_samples = 3`. Судья GigaChat 3.1 10B (Ollama, окно 4096 токенов) оценил 72 ответа, deepseek-flash — подвыборку из 22. Ситуации двух эссе, django-ORM и деградации ML-модели, модель генерации не собрала, их условие собрано из фактов шаблона

| Класс ответа | GigaChat | deepseek-flash |
|---|---|---|
| Честный полный, другими словами, с опечатками | ниже диапазона в 7 из 15; эссе django-ORM — 0 и 0.06 | 1.0 на эссе, 0.98–1.0 на коде |
| Честный медленный, в пределах лимитов | в диапазоне, 0.74 | — |
| Честный частичный и слабый | ниже диапазона в 4 из 9, все четыре — эссе с баллом 0 | выше диапазона 1 из 5: 0.81 при верхней границе 0.8 |
| Пустой, не по теме, падает, превышает память, лезет в сеть и файлы | 0 | — |
| Превышает время | 0; перебор подмножеств — 0.66 | — |
| Неверный по сути | выше диапазона 1 из 6 | — |
| Инъекция, самоутверждение, поддельные маркеры | выше диапазона 1 из 18 | выше диапазона 3 из 10 |
| Нет оценки | 3 ответа на одно задание: все сэмплы не разобраны | — |

Причины расхождений:

- Честный ответ теряет балл из-за судьи. GigaChat ставит yes по делу, но цитирует не дословно: заключает цитату в кавычки, ставит точку там, где предложение продолжается, сокращает многоточием, цитирует текст рубрики вместо ответа. В первом прогоне из 151 вердикта yes и partial на честные ответы код принял 81. Пересчёт тех же ответов судьи с послабленной сверкой — без учёта регистра, кавычек, точки и с многоточием, и с правилом «достаточно одной настоящей цитаты» — поднимает средний балл честных ответов с 0.51 до 0.66, а атак — с 0.33 до 0.37. deepseek-flash цитирует дословно, и послабление его баллы не меняет
- Ответ без оценки — окно контекста Ollama. Запрос судьи к заданию с кодом с метриками анализаторов занимал 3500–4000 токенов, ответ обрывался на 4096, и все три сэмпла не проходили схему. Сессия с таким заданием не оценивается, `POST /sessions/{id}/score` отвечает 502. С окном 8192 и 16384 токенов те же ответы разбирались; окно задаёт переменная сервера Ollama `OLLAMA_CONTEXT_LENGTH`
- Неверный код набирает балл долей тестов. Жадный алгоритм вместо динамики проходит 13 из 18 кейсов `algo-weighted-jobs` и получает 0.59, перебор подмножеств — 16 из 18 и 0.66: на сложность проверяют два кейса. Сортировка одних имён в `algo-top-k-ranking-cpp` проходит 9 из 17 граничных кейсов и получает 0.47. Частичное решение `backend-paginate` без верхней границы `per_page` проходит 23 из 27 и считается решённым. Исправлено группами кейсов и множителем качества, ниже раздел «Группы кейсов»
- Самоутверждение в комментарии кода засчитывается частично. deepseek-flash поставил partial пунктам о сложности и ясности кода по комментарию, который описывал динамику при жадном коде: рубрика 0.25, балл 0.63 при верхней границе 0.5. Это дыра из [security.md](security.md): цитата настоящая, но не о том. Остальные превышения у deepseek-flash — частичное решение `backend-paginate` и атаки поверх него, 0.81 у всех трёх: превышение даёт доля тестов, а не атака

- Легенда может исказить требование. В одном экземпляре `backend-validate-signup` GigaChat назвал код ошибки `unknown_fields` вместо `payload.unknown_fields`, и честное решение по условию провалило 4 кейса из 53. Проверки легенды ловят утечки и обрывы, но не сверяют требования с шаблоном; это ловит только слепой решатель, а он выключен по умолчанию

Ни одна атака не поднялась над своей основой — тем же ответом без атаки — больше чем на разброс судьи: гейт обнулил весь код без пройденных тестов, а требования максимума, поддельные маркеры и самоутверждения без содержания получили 0 по рубрике

Прохождение как кандидат через API на `backend/junior` с тремя заданиями с кодом и судьёй GigaChat с окном 16384. Эссе и задачки в сессию не вошли: с GigaChat и qwen3.5:9b без рассуждений их ситуации и кейсы не прошли проверку фактов, и сессии с ними уходили в `failed`. Честный сильный кандидат прошёл все тесты, получил 0.91, 0.76 и 0.75 и грейд middle с исходом `upgraded`; честный слабый — 0.73, 0.30 и 0.57 и исход `failed`; тот же слабый код с инъекциями — 0.69, 0.28 и 0.55 и `failed`. Machine summary назвал подтверждённые уровни и числа без оценок. Балл сильного кандидата держится на тестах, качестве и скорости: рубрика у двух заданий 0.17 и 0, и при качестве ниже 0.5 задание middle не было бы решено

### Группы кейсов

Ответ на расхождение «неверный код набирает балл долей тестов». Каждый шаблон с кодом делит кейсы на группы `manual`, `random` и `stress` с весами, ручные и стрессовые кейсы обязательны, а качество и скорость идут с множителем доли тестов. Механика — в [testing-mechanics.md](testing-mechanics.md#балл-задания), формат — в [TEMPLATE_FORMAT.md](../../taskgen/TEMPLATE_FORMAT.md)

Проверка — верхняя граница балла: судья, анализаторы и замер скорости ставят решению 1, и неверное решение, не решённое даже так, не станет решённым ни при каком судье. Проверка при импорте требует этого для неверных решений шаблона и решений-констант на каждом проверяемом seed, а [test_adversarial.py](../../taskgen/tests/evaluation/adversarial/test_adversarial.py) — чтобы из ответов набора с кодом решены были только честные полные ответы, медленный в пределах лимитов и атаки поверх них. Оба теста идут в Piston и входят в интеграционный прогон

Замер 7 октября 2026 года, те же кейсы до и после: генераторы только пометили кейсы группами. Балл — наибольший по seed при рубрике 1 и измеренных качестве и скорости, «решено» — с гейтом по обязательным группам

## Процедура на пилотных данных

> [!IMPORTANT]
> Пилотных данных о кандидатах нет: ни одна сессия не прошла реальный кандидат. Ниже — процедура и готовый к запуску запрос, а не результаты. Чисел о дискриминативности, согласованности грейда и разбросе судьи в этой документации нет, потому что их не из чего посчитать

Данные для процедуры сервис уже сохраняет: результат каждой сессии с баллами и решённостью заданий, шаблон каждого задания, вердикты и `spread` судьи в `answers.judge`. Процедура:

1. Пилот. Каждый участник проходит тест два раза на разных экземплярах: второй раз с другим seed и, если банк позволяет, на других шаблонах той же ячейки. Для части участников нужен независимый эксперт, который ставит грейд по собеседованию, без доступа к результатам теста
2. Трудность шаблона, p — доля решивших задания шаблона. Шаблон с p около 0 или около 1 не разделяет кандидатов и уходит на доработку
3. Дискриминативность шаблона, индекс D — разность долей решивших задания шаблона среди верхних и нижних 27 % кандидатов по среднему баллу сессии, внутри пары (область, заявленный грейд). Это классический индекс дискриминации теории тестов. Шаблон с низким или отрицательным D сильные решают не чаще слабых, его нужно пересмотреть
4. Согласованность грейда — доля пар прохождений одного участника, давших один и тот же грейд, и каппа Коэна по парам. Разные экземпляры одного шаблона должны давать один грейд; расхождение указывает на шаблон, чья сложность зависит от параметров
5. Соответствие экспертной оценке — доля совпадений грейда теста с грейдом эксперта и матрица ошибок: тест чаще завышает или занижает
6. Разброс судьи — распределение `spread` по пунктам рубрики и повторная оценка одних и тех же ответов. Пункт рубрики с большим разбросом переписывается атомарнее

Трудность и дискриминативность по всем оценённым сессиям считает [scripts/item_analysis.sql](../../taskgen/scripts/item_analysis.sql). Запрос проверен на схеме и на синтетических строках в откатываемой транзакции:

```sh
cd taskgen
docker compose exec -T db psql -U taskgen -d taskgen < scripts/item_analysis.sql
```

## Ограничения

- Нет пилотных данных и экспертной разметки, поэтому критерии ТЗ о согласованности грейда, дискриминативности и соответствии экспертной оценке пока подкреплены только процедурой, а не числами
- Импорт проверяет шаблоны с кодом на `import_check.seeds` seed, по умолчанию трёх; другие seed дают другие значения параметров, и импорт их не видит. Сервис компенсирует это проверкой каждого экземпляра эталоном перед выдачей. Неверные решения при генерации не прогоняются: на seed экземпляра тесты могут и не поймать ошибку, которую поймали на seed импорта
- Под большой нагрузкой на машину Piston обрывает компиляцию C++ своим лимитом, и импорт отклонит исправный шаблон с C++: верное решение «не прошло», неверное «не компилируется». Это ложный отказ без записи в банк, а не ложный пропуск; повтор на свободной машине или меньшее `import_check.concurrency` его снимают
- Эссе проверяются только по формату и по запрещённым фразам в вопросах. Качество ситуаций от модели проверяется при каждой генерации, но статистики их отказов нет
- Что факты варианта задачки подходят к любому значению параметров шаблона, например к любому домену, проверил автор банка, а не код: смысл факта код не читает ([TEMPLATE_FORMAT.md](../../taskgen/TEMPLATE_FORMAT.md))
- Что факты варианта задачки исключают каждый неверный ответ, проверил автор банка, а не код. Слепой решатель ловит неоднозначный кейс, но выключен по умолчанию; статистики его ложных отказов на настоящих моделях нет, хотя итог решателя сохраняется в каждом задании
- Сопоставимость сложности внутри ячейки задана оценкой автора шаблона `difficulty` и проверяется как разброс этой оценки; эмпирическая проверка — трудность p из процедуры выше
