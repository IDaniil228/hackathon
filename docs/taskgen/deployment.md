# Сборка, развёртывание и локальный запуск taskgen

Все команды выполняются из каталога `taskgen/` репозитория. Состав контейнеров и порты задаёт [docker-compose.yml](../../taskgen/docker-compose.yml), настройки сервиса и их переменные окружения — [generated/settings.md](generated/settings.md), версии компонентов — [generated/libraries.md](generated/libraries.md)

## Что нужно

- Linux с cgroup v2 и Docker с Compose v2. Песочница Piston изолирует запуски через namespaces и cgroup, поэтому её контейнер работает в режиме `privileged`
- [uv](https://docs.astral.sh/uv/) и curl на хосте: на них работают скрипт установки пакетов песочницы и команды разработки
- OpenAI-совместимые провайдеры LLM. По умолчанию генератор, решатель и эмбеддинги работают в Ollama на хосте или в контейнере из профиля `ollama`, а судья, проверяльщик ситуации эссе и детектор ИИ — в облачном API DeepSeek, для него нужен ключ. Провайдера и модель каждой роли задают настройки группы `llm`
- Свободные порты, которые публикует `docker-compose.yml`

## 1. Ключи и модели

Создайте `taskgen/.env`: его читают и сервис в контейнере, и сервис, запущенный на хосте. Файл в `.gitignore`, ключ не попадёт в репозиторий:

```sh
cd taskgen
echo "TASKGEN_BOOTSTRAP_ADMIN_KEY=$(openssl rand -hex 32)" > .env
```

Этот ключ — первый ключ роли `admin`. Остальные ключи выпускает `POST /keys`, и сервис хранит их только хэшем

Сервис ходит к двум провайдерам: `ollama` и `deepseek`. Какая роль у какого провайдера и с какой моделью, по умолчанию видно в [generated/settings.md](generated/settings.md#llm). Ключ DeepSeek задаётся только переменной окружения:

```sh
echo "TASKGEN_LLM__PROVIDERS__DEEPSEEK__API_KEY=<ключ>" >> .env
```

Без ключа сервис стартует и пишет в журнал предупреждение с именем этой переменной. Вызов судьи или проверяльщика тогда завершается ошибкой с тем же именем и в сеть не уходит, а сервис считает модель недоступной: эссе и задачки не генерируются, ответы не оцениваются. Ключ не попадает ни в журнал, ни в документацию

Ollama на хосте сервис в контейнере достаёт через `host.docker.internal`. Ollama по умолчанию слушает только `127.0.0.1`, и из контейнера её не видно: запустите её с `OLLAMA_HOST=0.0.0.0:11434` и разрешите этот порт в межсетевом экране для сети Docker. Модели по умолчанию загружаются так:

```sh
ollama pull hf.co/ai-sage/GigaChat3.1-10B-A1.8B-GGUF:q4_K_M
ollama pull bge-m3
```

Ollama в контейнере вместо хоста поднимает профиль `ollama`. Тогда адрес провайдера — имя сервиса в сети Compose, а модели загружаются внутри контейнера:

```sh
echo "TASKGEN_LLM__PROVIDERS__OLLAMA__BASE_URL=http://ollama:11434/v1" >> .env
docker compose --profile ollama up -d ollama
docker compose exec ollama ollama pull hf.co/ai-sage/GigaChat3.1-10B-A1.8B-GGUF:q4_K_M
docker compose exec ollama ollama pull bge-m3
```

У всех ролей по умолчанию `reasoning_effort: "none"`. Модели с рассуждениями на слабой машине могут истратить весь ответ на рассуждения и вернуть пустой текст: при проверке этой инструкции qwen3.5:9b без этой настройки не написал условие первого задания ни с одной попытки, и `POST /sessions` ответил 502, а с `none` та же сессия создалась за 18 секунд. GigaChat 3.1 в Ollama рассуждать не умеет и на любое другое значение отвечает 400 `does not support thinking`

Окно контекста Ollama задаёт сервер, а не запрос: OpenAI-совместимый API Ollama не принимает `num_ctx`. При малой видеопамяти Ollama 0.32 берёт окно 4096 токенов. Запрос судьи к заданию с кодом — условие, рубрика, метрики анализаторов и сам код — занимал на проверке 3500–4000 токенов, и ответ обрывался на 4096 с `finish_reason: length`. Обрезанный JSON не проходит схему, а если так обрываются все сэмплы, сессия не оценивается и `POST /sessions/{id}/score` отвечает 502. С окном 8192 те же запросы разобрались все. Поэтому Ollama для сервиса запускается с `OLLAMA_CONTEXT_LENGTH=16384`, профиль `ollama` в `docker-compose.yml` уже задаёт это значение

### Другие провайдеры и полностью локальный режим

Модель роли задаётся одной строкой `провайдер/модель`: часть до первого `/` — имя провайдера, остальное — имя модели у него, и в именах Ollama бывают свои `/`. Роль переезжает к другому провайдеру переменной окружения, без правки кода. Новый провайдер появляется вместе с адресом, например `TASKGEN_LLM__PROVIDERS__VLLM__BASE_URL=http://gpu:8000/v1`, а роль называет его префиксом: `TASKGEN_LLM__JUDGE__MODEL=vllm/<модель>`. Одна и та же модель может работать у двух провайдеров сразу. Модель с провайдером, которого нет в `llm.providers`, — ошибка конфигурации: сервис не стартует и называет роль и известных провайдеров. Провайдер должен отдавать OpenAI-совместимые `/chat/completions` и, если у него эмбеддинги, `/embeddings`. Если провайдер отвечает 4xx на `response_format` типа `json_schema`, сервис повторяет запрос со схемой в тексте и разбирает JSON из ответа. Провайдеру, о котором это известно заранее, поле `llm.providers.<имя>.structured_output` даёт сразу второй путь и экономит запрос. У DeepSeek по умолчанию там `json_object`: DeepSeek отвечает 400 на `json_schema`, а с `json_object` возвращает валидный JSON с первого запроса. YandexGPT и облачный GigaChat с сервисом не проверялись. Облачному провайдеру можно поднять лимит одновременных запросов `TASKGEN_LLM__PROVIDERS__<ИМЯ>__CONCURRENCY`

Облачный ключ для работы не обязателен. Для полностью локального режима достаточно переназначить облачные роли на модель Ollama, например на ту же GigaChat:

```sh
TASKGEN_LLM__JUDGE__MODEL=ollama/hf.co/ai-sage/GigaChat3.1-10B-A1.8B-GGUF:q4_K_M
TASKGEN_LLM__CHECKER__MODEL=ollama/hf.co/ai-sage/GigaChat3.1-10B-A1.8B-GGUF:q4_K_M
TASKGEN_LLM__DETECTOR__MODEL=ollama/hf.co/ai-sage/GigaChat3.1-10B-A1.8B-GGUF:q4_K_M
```

Облачный провайдер за рубежом получает условия заданий и ответы кандидатов, и если в них есть персональные данные кандидатов, передача требует отдельного разбора на соответствие 152-ФЗ

## 2. Контейнеры

```sh
docker compose up -d --build
```

Поднимаются Postgres с pgvector, Piston и сервис. Сервис при старте применяет миграции (`alembic upgrade head`), они же создают справочники областей, грейдов и навыков

## 3. Пакеты песочницы

Свежий Piston не умеет ни одного языка. Скрипт ставит пакеты всех окружений из реестра: официальные — через API Piston, локальный `python-ml` с NumPy, scikit-learn и PyTorch — сборкой из [sandbox/packages](../../taskgen/sandbox/packages). Первая сборка `python-ml` скачивает около гигабайта и идёт несколько минут; архив кэшируется и при повторной установке не собирается:

```sh
sandbox/piston-packages.sh install
```

По умолчанию скрипт ищет контейнер `taskgen-piston-1` и Piston на `localhost:2000`; для другого имени проекта Compose или порта есть флаги `-c` и `-u`, справка — `sandbox/piston-packages.sh --help`. Скрипт перезапускает контейнер Piston, потому что Piston читает локальные пакеты только при старте

## 4. Банк шаблонов

```sh
docker compose exec taskgen taskgen import seed/templates
```

Импорт проверяет все шаблоны и пишет их одной транзакцией: при любой ошибке не пишется ничего, а ошибки всех файлов выводятся сразу. Шаблоны с кодом проверяются в Piston, поэтому Piston с пакетами окружений из шага 3 нужен до импорта; если он недоступен, импорт завершается кодом 3 и ничего не пишет. На банк из `seed/templates` проверка тратит около минуты. Затем считаются эмбеддинги описаний. Если модель эмбеддингов недоступна, импорт всё равно проходит, а отбор шаблонов идёт по доле общих навыков; эмбеддинги досчитает следующий импорт. Ключ `--no-embeddings` пропускает их сразу. Тот же банк загружается через API: `POST /templates/bulk` с ключом `admin`

## 5. Проверка

```sh
curl localhost:8000/health
```

Ответ `{"status":"ok"}` значит, что сервис запущен. Swagger UI открывается по адресу `http://localhost:8000/docs`. Ключ роли `client` для основного бэкенда выпускает admin:

```sh
curl -X POST localhost:8000/keys \
  -H "Authorization: Bearer $(sed -n 's/^TASKGEN_BOOTSTRAP_ADMIN_KEY=//p' .env)" \
  -H 'Content-Type: application/json' \
  -d '{"name": "backend", "role": "client"}'
```

Ключ из ответа показывается один раз. С ним `GET /templates` возвращает метаданные банка. Перед первой сессией проверьте, что Ollama доступна из контейнера сервиса: при недоступной модели `POST /sessions` ждёт таймаута запроса к ней на каждой попытке и только потом отвечает ошибкой 502:

```sh
docker compose exec taskgen python -c \
  "import httpx; print(httpx.get('http://host.docker.internal:11434/v1/models', timeout=5).status_code)"
```

## Запуск сервиса на хосте

Для разработки сервис запускается из исходников, а Postgres и Piston — в контейнерах:

```sh
docker compose up -d db piston
sandbox/piston-packages.sh install
uv sync
uv run alembic upgrade head
uv run taskgen import seed/templates
uv run taskgen serve
```

Сервис на хосте берёт настройки из переменных окружения и из `.env` в рабочем каталоге; значения по умолчанию указывают на `localhost`, так что Ollama на хосте доступна без `OLLAMA_HOST`. При старте сервис подхватывает незавершённые сессии и пополняет пул готовых экземпляров: на слабой машине пополнение надолго занимает модель, `TASKGEN_GENERATION__POOL_SIZE=0` его выключает. Сервис рассчитан на один процесс на одну БД: не запускайте его одновременно на хосте и в контейнере с общей базой

## Тесты и линтеры

```sh
uv run pytest -q -m "not integration"
uv run pytest -q
uv run ruff check . && uv run ruff format --check .
```

Первая команда не требует ничего, кроме Python. Полный прогон требует Postgres и Piston с пакетами: адрес БД задаёт `TASKGEN_DATABASE_URL`, адрес Piston — `TASKGEN_SANDBOX__PISTON_URL`. Тесты с настоящей моделью включает `TASKGEN_LLM_SMOKE=1`. Справочники документации пересобирает `uv run python scripts/gen_docs.py`, и тест `tests/test_docs_generated.py` падает, если их забыли пересобрать

В CI линтеры и тесты без метки `integration` запускает [taskgen.yml](../../.github/workflows/taskgen.yml), а тесты с меткой `integration` — [taskgen-integration.yml](../../.github/workflows/taskgen-integration.yml). Когда запускается каждый из них и почему, сказано в заголовке файла

## Ограничения образа

- Образ сервиса не ставит clang-tidy и cppcheck: метрики качества C++ из этих инструментов в контейнере не измеряются, и их вес переходит к остальным компонентам балла. lizard ставится как зависимость Python
- Образы Piston и Ollama, базовый образ uv в `Dockerfile` не закреплены тегом версии и берутся как `latest`
